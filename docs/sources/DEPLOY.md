# 发布与部署

本文说明本仓库的主站（Main）如何从一个镜像发布到单台 Docker 主机：为什么这样设计、应用为此提供了什么、发布脚本按什么顺序执行、每一步失败后留下什么。工具本身的用法见 [deploy/sources/README.md](../../deploy/sources/README.md)，代码在 `deploy/sources/deploy.py`。

## 目标

- **一条命令发布**：`deploy.py main <镜像>` 完成预检、迁移、启动新实例、后台交接、切流、自动守护和退役旧实例，中间无需人工操作。
- **用户请求不中断**：已建立的流式连接和已受理的异步任务不被截断。
- **可回滚**：守护期内发现问题自动回滚；守护期后一条命令回到上一版本。
- **工具不随版本改动**：连续发布不需要修改发布脚本或 Nginx 配置。

## 构建

打 `v*` tag 后，`.github/workflows/release.yml` 从固定提交构建：`scripts/sources_release/build.sh` 要求工作树干净，使用锁定的依赖构建前端、Portal 和后端；`ci_gate.py` 核对该提交的 CI 结果；`publish.py` 只发布一次镜像，已发布的摘要不覆盖。部署时按摘要引用镜像。

## 为什么用固定槽位

如果容器名、端口和 Nginx upstream 名都带版本号，每次发布都要新开端口、改写多处 Nginx 引用、给静态资源接一段新的兜底链，发布脚本也就要随版本修改。因此改为固定的结构：

- **两个槽位 A、B 轮流使用。** 每个槽位三个容器：serving 主、serving 备和 background。容器名固定为 `<前缀>-{a,b}-{serving,standby,background}`，每个槽位的端口在配置里固定。
- **新版本总是发到“非当前”槽位。** 那里原有的容器是上上个版本，发布时直接删除重建；上一个版本留在另一个槽位，停止后保留，用于回滚。所以任何时候只保留一个可回滚的上一版本。
- **Nginx 只引用两个固定 upstream 名**：`sources_main_serving`（主 + 备，备用 `backup`）和 `sources_main_admin`（后台）。切流时只重写一个由脚本生成的 upstream 文件，其他 Nginx 配置不再变化。预检会拒绝仍在引用按版本命名的 upstream 的配置。
- **静态资源放在一个固定目录。** 文件名带内容哈希，新版本的资源追加复制进去，不删除也不覆盖，所以切换后仍停留在旧页面的浏览器能继续加载旧资源。
- **内部调用方使用固定别名。** 每个 serving 容器在所有网络上带同一个网络别名（默认 `sources-main-serving`），后台容器没有。旧版本退役后自动从该名字的解析结果中消失，内部服务（如 Portal）不会被绑在某个旧容器的地址上。
- 服务器上只有一个状态文件记录当前槽位、上一槽位、镜像和进行中的步骤；每次运行在 `history.jsonl` 追加一行结果和各步骤耗时。

## 进程角色与唯一后台

同一个镜像以两种角色运行，由环境变量 `SOURCES_PROCESS_ROLE` 区分：

- **serving**：处理用户和 API 请求，不运行后台任务。主、备两个实例同时就绪，主实例故障时 Nginx 自动转到备实例。
- **background**：运行全部后台服务（定时任务、渠道监控、OAuth 刷新、媒体引擎等）并处理需要它们的管理接口。

同一时刻只能有一个后台。这由操作系统文件锁保证：background 在构造任何依赖之前对锁目录中的 `native-background.lock` 加 `flock`，媒体引擎存储在打开时再取一把自己的锁。进程退出时内核自动释放锁，所以新后台只有在旧后台真正退出后才能拿到锁。发布脚本只负责安排顺序，不需要证明“没有两个后台”，也从不发送 SIGKILL。

每个实例通过内部接口 `/internal/sources/runtime` 报告角色、`ready` 和 `owns_background`；`/internal/sources/drain` 让 serving 实例进入排空状态。两个接口都需要运行令牌。

## 应用为发布提供的支持

- **后台优雅退出。** 收到 SIGTERM 后，应用先关闭 HTTP，再并行停止所有后台服务，等在途任务完成后退出：
  - OAuth 刷新停止时不再发起新的刷新，但不取消已经在和供应商通信的刷新，等它们保存新凭据后再返回（单次刷新有超时上限）。否则供应商已轮换 refresh token 而新凭据被丢弃，账号下次刷新会失败。
  - 渠道探测和定时测试停止时立即取消在途探测；被取消的探测不写历史，避免交接产生假的“失败”记录。
  - 媒体引擎只等已领取的操作完成；新任务留在共享存储中，由下一个后台领取。提交结果不明的任务标为 unknown，不重发。
- **一次性命令**（`backend/cmd/server/sources_deploy_commands.go`）。它们都不监听端口、不取后台锁、不启动后台服务，并且只输出一行带固定前缀的结果供脚本读取：
  - `-list-pending-migrations`：只读迁移账本，输出 `SOURCES_PENDING_MIGRATIONS a.sql,b.sql`，供 `-migrate-only` 使用。
  - `-check-startup`：用 serving 语义、临时锁目录和临时令牌，按生产配置构造全部依赖后退出，输出 `SOURCES_STARTUP_CHECK_OK {...}`。有待执行迁移时会失败，所以脚本先迁移再检查。
  - `-export-web-assets <目录>`：把镜像内嵌的前端资源复制到指定目录（只追加、不覆盖），保证 HTML 与资源来自同一次构建。
- **只扩展的迁移。** 新迁移在旧版本仍在服务时执行，所以只能新增表、可空或带默认值的列和索引。`deploy/sources/migration_lint.py` 在 CI 中拒绝删除表或列、改名、改列类型、`SET NOT NULL` 和 `TRUNCATE`，除非文件名包含 `contract`；经审查的例外（例如原版同步带来的语句）登记在 `deploy/sources/migration-allow.txt` 并写明原因。带 `contract` 的迁移只有加 `--allow-contract` 才会执行。

## 发布顺序

整个命令持有发布锁，防止并发发布。上一次运行没有走完（状态里 `in_progress` 不为空）时，新的发布会拒绝执行，需要先人工确认现场。

| 步骤 | 内容 | 失败时留下什么 |
| --- | --- | --- |
| 拉取镜像 | 本地没有时按引用拉取 | 现场不变 |
| 预检 | Nginx 已使用固定 upstream；目标槽位不是当前槽位、没有仍在排空的容器；目标端口可绑定且（落在临时端口范围时）已被保留；宿主可用内存足够；用新镜像列出待执行迁移；有 `contract` 迁移而未加参数则拒绝 | 现场不变，没有创建任何容器 |
| 迁移 | 有待执行迁移时，用新镜像以 background 环境执行 `-migrate-only` | 退出；迁移只扩展结构，旧版本继续服务 |
| 启动检查 | 分别用 serving 和 background 两套环境运行 `-check-startup`，两套环境的配置错误都在这里暴露 | 退出，没有创建 serving 容器；已执行的迁移保留（旧版本兼容） |
| 导出静态资源 | `-export-web-assets` 导出到临时目录，再追加进固定资源目录 | 退出；资源目录只多了新文件 |
| 启动新 serving | 删除目标槽位的旧容器，创建并启动主、备两个 serving，等待就绪 | 删除新 serving 容器，退出；旧版本继续服务 |
| 后台交接 | 旧后台改为不自动重启，发送一次 SIGTERM，等它处理完在途任务后自行退出；然后启动新后台，等待 `ready` 且 `owns_background` | 新后台在超时内未就绪或容器退出：停止新后台，重新启动旧后台，删除新 serving，退出 |
| 切流 | 生成新的 upstream 文件，`nginx -t` 通过后 reload 一次；旧 worker 继续服务已建立的连接直到结束 | `nginx -t` 失败：恢复原文件，后台交还旧版本，删除新 serving，退出 |
| 守护 | 默认 5 分钟、每 10 秒检查一次（见下节） | 自动回滚（见下节） |
| 退役 | 旧 serving 改为不自动重启，发起排空，再发送 SIGTERM，不等待；它处理完已转来的请求（包括流式连接）后自行退出。更新状态文件，追加历史 | — |

`--dry-run` 只打印会执行的变更命令；只读步骤（列出迁移、启动检查）照常执行。

## 自动守护与回滚

切流后检查新 serving 主实例。以下任一情况视为失败（阈值均可在配置中调整）：

- 运行时接口不再报告 `ready`；
- 容器重启或被 OOM 终止；
- 内存超过容器上限的 70%，或 30 秒内上涨超过 4 GiB；
- 公网健康检查连续 3 次失败；
- Nginx 错误日志里连接新实例端口失败（连接拒绝、upstream 超时）累计达到 10 次。

上游供应商返回的 502、503、429 不算失败：它们在切流前后都可能出现，守护只看 Nginx 能不能连上应用。

守护失败时，脚本立即把 upstream 文件切回上一槽位并 reload，把后台交还旧版本，然后停止新 serving 并**保留**这些容器供排查。

守护期过后的回滚使用 `deploy.py rollback`：它复用上一槽位已停止的容器（不重新创建），按同样的顺序执行启动、后台交接、切流、守护和退役。

守护只能发现切流后几分钟内的问题。常驻监测由 `deploy.py watch`（systemd 单元 `sources-main-watch.service`）负责：每 10 秒对当前版本采样健康状态、重启、OOM、内存和活跃请求数，超过阈值时向 journal 写一条预警。

## 无法自动恢复的情况

如果恢复步骤本身也失败（例如切回旧槽位时 `nginx -t` 失败，或新后台失败后旧后台也无法重新就绪），脚本报告 `FAILED AND NOT RESTORED` 并保留 `in_progress`。此时下一次发布会被拒绝，需要人工用 `deploy.py status` 和 `docker ps` 查看现场、恢复服务后再清除该标记。

## 已知取舍

- 后台交接期间，管理接口和后台任务会暂停到新后台就绪；用户请求不受影响，新的图片任务照常受理并在新后台起来后执行。
- 守护只覆盖切流后的短时间窗口，较晚出现的问题依赖常驻监测和 serving 的主备结构。
- 只在后台持锁时才执行的分支（应用迁移、以引擎方式打开媒体引擎）无法被 `-check-startup` 覆盖，由后台交接的自动回退兜底。
- 本方案针对单台主机。若以后扩展到多台主机，可以把文件锁换成 PostgreSQL 会话级 advisory lock（连接断开时同样自动释放），其余设计不变。
