# 发布与部署

本文说明本仓库的主站（Main）如何从一个镜像发布到单台 Docker 主机：为什么这样设计、应用为此提供了什么、发布脚本按什么顺序执行、每一步失败后留下什么。工具本身的用法见 [deploy/sources/README.md](../../deploy/sources/README.md)，代码在 `deploy/sources/deploy.py`。

## 目标

- **一条命令发布**：`deploy.py main <镜像>` 完成预检、迁移、启动新实例、后台交接、切流、自动守护和退役旧实例，中间无需人工操作。
- **用户请求不中断**：已建立的流式连接和已受理的异步任务不被截断。
- **可回滚**：守护期内发现问题自动回滚；守护期后一条命令回到上一版本。
- **工具不随版本改动**：连续发布不需要修改发布脚本或 Nginx 配置。

## 构建

打 `v*` tag 后，`.github/workflows/release.yml` 从固定提交构建：`scripts/sources_release/build.sh` 要求工作树干净，使用锁定的依赖构建前端、Portal 和后端；`ci_gate.py` 核对该提交的 CI 结果；`publish.py` 只发布一次镜像，已发布的摘要不覆盖。部署时按摘要引用镜像。

## 为什么用固定槽位

如果容器名、端口和 Nginx upstream 名都带版本号，每次发布都要新开端口、改写多处 Nginx 引用、给静态资源接一段新的兜底链，发布脚本也就要随版本修改。因此改为固定的结构：

- **两个槽位 A、B 轮流使用。** 每个槽位三个容器：serving 主、serving 备和 background。容器名固定为 `<前缀>-{a,b}-{serving,standby,background}`，每个槽位的端口在配置里固定。
- **新版本总是发到“非当前”槽位。** 那里原有的容器是上上个版本，发布时直接删除重建；上一个版本留在另一个槽位，停止后保留，用于回滚。所以任何时候只保留一个可回滚的上一版本。
- **Nginx 只引用两个固定 upstream 名**：`sources_main_serving`（主 + 备，备用 `backup`）和 `sources_main_admin`（后台）。切流时只重写一个由脚本生成的 upstream 文件，其他 Nginx 配置不再变化。预检会拒绝仍在引用按版本命名的 upstream 的配置。
- **静态资源放在一个固定目录。** 文件名带内容哈希，新版本的资源追加复制进去，不删除也不覆盖，所以切换后仍停留在旧页面的浏览器能继续加载旧资源。
- **内部调用方使用固定别名。** 正式接流的 serving 容器在所有网络上带同一个网络别名（默认 `sources-main-serving`）。暂停时，共享别名仍由已有版本提供。旧版本退役后自动从该名字的解析结果中消失，内部服务（如 Portal）可沿用固定别名。
- 服务器上只有一个状态文件记录当前槽位、上一槽位、镜像和进行中的步骤；每次正式运行在 `history.jsonl` 追加一行结果和各步骤耗时，演练（`--dry-run`）不写历史。

## 进程角色与唯一后台

同一个镜像以两种角色运行，由环境变量 `SOURCES_PROCESS_ROLE` 区分：

- **serving**：处理用户和 API 请求，不运行后台任务。主、备两个实例同时就绪，主实例故障时 Nginx 自动转到备实例。
- **background**：运行全部后台服务（定时任务、渠道监控、OAuth 刷新、媒体引擎等）并处理需要它们的管理接口。

同一时刻只能有一个后台。这由操作系统文件锁保证：background 在构造任何依赖之前对锁目录中的 `native-background.lock` 加 `flock`，媒体引擎存储在打开时再取一把自己的锁。进程退出时内核自动释放锁，所以新后台只有在旧后台真正退出后才能拿到锁。发布脚本只负责安排顺序，不需要证明“没有两个后台”，也从不发送 SIGKILL。

每个实例通过内部接口 `/internal/sources/runtime` 报告角色、`ready` 和 `owns_background`；`/internal/sources/drain` 让 serving 实例进入排空状态。两个接口都需要运行令牌。background 还报告 `admin_during_drain`（值为 `read-only`，表示排空期间管理接口只读，见下节）、`active_admin_writes`（排空期间会被拒绝、仍在处理的管理请求数）和 `stopping`（尚未停完的后台服务）。定时备份创建期间还报告 `scheduled_backup_remaining_seconds`，用剩余秒数表示原执行期限。到期后仍在收尾时报告 `0`，创建阶段结束后省略。对 background 调用 `/internal/sources/drain` 同样会让它进入只读排空，直到进程退出；发布工具只对 serving 调用这个接口。

## 应用为发布提供的支持

- **后台优雅退出。** serving 和 standalone 收到 SIGTERM 后先关闭 HTTP，等在途请求结束，再停止各项服务后退出，顺序不变。background 不同，它在停止后台服务的整个过程中保持监听，让管理页面在交接期间继续可用：
  1. 进入只读排空：管理接口只应答 `GET` 和 `HEAD`。其它方法、MCP（`/api/v1/mcp`）、WebSocket 升级，以及少数 `GET`——媒体引擎审阅（它读的存储会在第 3 步关闭）和会访问上游供应商的查询（账号用量的主动查询、刷新余额、OpenAI/Grok/国内供应商额度与余额、Claude 重置额度、账号模型列表；它们会探测上游、可能刷新并保存 OAuth 凭据、写账号状态或启动超出请求的后台工作，清单在 `processrole/handoff.go`）——在进入处理器之前返回 503，使用原生错误信封（`reason` 为 `BACKGROUND_HANDOFF_READ_ONLY`，`message` 说明正在发版、暂时只读、请稍后重试），带 `Retry-After: 5`。请求没有执行任何部分，所以重试总是安全的。只读是因为写请求可能把工作交给已经停止的服务，或启动进程退出时会被截断的 goroutine。
  2. 等 SIGTERM 之前已经进入、排空期间会被拒绝的管理请求（写、MCP、上面那些会访问上游的查询；WebSocket 除外）处理完，与原来“先等在途请求、再停服务”的顺序一致。
  3. 并行停止所有后台服务，按下面各项的规则等待在途工作。
  4. 结束打开着的管理 WebSocket：取消它们的请求上下文，运维实时页发送关闭帧后自动重连。否则被劫持的连接不会随 HTTP 关闭而结束，会一直拖住进程退出。
  5. 关闭 HTTP 监听，等在途读请求结束，停止其余服务（用量、计费缓存、OAuth、日志等）和 Redis、数据库连接，退出。锁仍然只在进程退出时由内核释放。

  管理界面与 API 同源部署时浏览器不发 CORS 预检；如果跨源部署，排空期间的 `OPTIONS` 预检同样得到不带 CORS 头的 503，浏览器会把它当作网络错误显示。

  排空期间 `/health` 照常返回 200：进程仍在应答管理读请求。是否就绪以运行时接口为准：排空时 `ready` 为 false、`draining` 为 true。常驻监测和巡检读 `/health` 时，这段时间不会被当作故障。

  各后台服务停止时：
  - OAuth 刷新停止时不再发起新的刷新，但不取消已经在和供应商通信的刷新，等它们保存新凭据后再返回（单次刷新有超时上限）。否则供应商已轮换 refresh token 而新凭据被丢弃，账号下次刷新会失败。
  - 渠道探测和定时测试停止时立即取消在途探测；被取消的探测不写历史，避免交接产生假的“失败”记录。
  - 媒体引擎只等已领取的操作完成；新任务留在共享存储中，由下一个后台领取。提交结果不明的任务标为 unknown，不重发。
  - 定时备份的 dump、上传和完成记录沿用原有的两小时执行期限。已经开始的创建会完成或到达自身执行期限，旧后台随后才能退出。手动备份、恢复和过期备份清理仍走原有的停机等待与取消流程。
- **一次性命令**（`backend/cmd/server/sources_deploy_commands.go`）。它们都不监听端口、不取后台锁、不启动后台服务，并且只输出一行带固定前缀的结果供脚本读取：
  - `-list-pending-migrations`：只读迁移账本，输出 `SOURCES_PENDING_MIGRATIONS a.sql,b.sql`，供 `-migrate-only` 使用。
  - `-check-startup`：用 serving 语义、临时锁目录和临时令牌，按生产配置构造全部依赖后退出，输出 `SOURCES_STARTUP_CHECK_OK {...}`。有待执行迁移时会失败，所以脚本先迁移再检查。
  - `-export-web-assets <目录>`：把镜像内嵌的前端资源复制到指定目录（只追加、不覆盖），保证 HTML 与资源来自同一次构建。
- **只扩展的迁移。** 新迁移在旧版本仍在服务时执行，所以只能新增表、可空或带默认值的列和索引。`deploy/sources/migration_lint.py` 在 CI 中拒绝删除表或列、改名、改列类型、`SET NOT NULL` 和 `TRUNCATE`，除非文件名包含 `contract`；经审查的例外（例如原版同步带来的语句）登记在 `deploy/sources/migration-allow.txt` 并写明原因。带 `contract` 的迁移只有加 `--allow-contract` 才会执行。

## 发布顺序

整个命令持有发布锁，防止并发发布。上一次运行没有走完（状态里 `in_progress` 不为空）时，新的发布会拒绝执行，需要先人工确认现场。

`deploy.py main` 在拉镜像或跑迁移前、`deploy.py rollback` 在启动上一槽位前，都会读取当前后台的定时备份状态。发现正在创建备份时，预检默认中止。两个命令都可用 `--allow-running-backup` 继续，管理写入将等旧后台完成排空。预检后才启动的备份同样会排空。旧后台还不支持备份状态和排空保护时，应避开定时备份时段升级。

| 步骤 | 内容 | 失败时留下什么 |
| --- | --- | --- |
| 拉取镜像 | 本地没有时按引用拉取 | 现场不变 |
| 预检 | Nginx 已使用固定 upstream；目标槽位不是当前槽位、没有仍在排空的容器；目标端口可绑定且（落在临时端口范围时）已被保留；宿主可用内存足够；用守护阶段完全相同的请求访问公网健康地址，必须返回 200；用新镜像列出待执行迁移；有 `contract` 迁移而未加参数则拒绝 | 现场不变，没有创建任何容器 |
| 迁移 | 有待执行迁移时，用新镜像以 background 环境执行 `-migrate-only` | 退出；迁移只扩展结构，旧版本继续服务 |
| 启动检查 | 分别用 serving 和 background 两套环境运行 `-check-startup`，两套环境的配置错误都在这里暴露 | 退出，没有创建 serving 容器；已执行的迁移保留（旧版本兼容） |
| 导出静态资源 | `-export-web-assets` 导出到临时目录，再追加进固定资源目录 | 退出；资源目录只多了新文件 |
| 启动新 serving | 删除目标槽位的旧容器，创建并启动主、备两个 serving，等待就绪 | 删除新 serving 容器，退出；旧版本继续服务 |
| 后台交接 | 旧后台改为不自动重启，收到一次 SIGTERM 后处理完在途任务并退出。支持只读排空的旧后台继续提供普通管理读接口，旧版本在排空期间可能中断管理读。发布工具每 0.5 秒核对容器状态，并定期查询定时备份状态。状态查询失败时退避重试。备份完成后仍给租约释放和进程退出留出收尾时间。Docker 确认旧后台退出或容器已移除后，新后台才启动并持锁就绪。`inspect` 和后备的容器列表查询共用当前等待窗口的剩余时间 | 发送 SIGTERM 返回失败时，限时确认停止服务或容器退出。新后台就绪超时后的回退使用同一规则。已确认关闭但超过常规等待期 `background_exit_timeout`（默认 2100 秒）和适用的备份等待期时，查询、恢复后台和清理新 serving 共用同一个 30 秒恢复窗口 |
| 切流 | 生成新的 upstream 文件，`nginx -t` 通过后 reload 一次；旧 worker 继续服务已建立的连接直到结束 | `nginx -t` 失败：恢复原文件，后台交还旧版本，删除新 serving，退出 |
| 守护 | 默认 5 分钟、每 10 秒检查一次（见下节） | 自动回滚（见下节） |
| 退役 | 旧 serving 改为不自动重启，发起排空，再发送 SIGTERM，不等待；它处理完已转来的请求（包括流式连接）后自行退出。更新状态文件，追加历史 | — |

`--dry-run` 是全局参数，写在子命令之前（`deploy.py --dry-run main <镜像>`）。它只打印会执行的变更命令；只读步骤（列出迁移、启动检查）照常执行。有待执行迁移时，演练不会执行迁移，而启动检查拒绝带待执行迁移的数据库，所以演练跳过启动检查并在输出中写明；两个环境的配置要到正式运行时，在迁移之后、创建任何容器之前才第一次校验。公网健康检查是只读请求，演练同样会执行，所以演练能发现守护阶段必然失败的公网检查。失败的演练没有改变任何东西，不在 `history.jsonl` 留下记录，以免和失败的正式发布混淆。

### 公网健康预检

公网健康地址（`main.json` 的 `public_health_url`）在切流前后用同一个请求检查。所有请求都带固定的 `User-Agent`：公网入口前的部分边缘防护会拒绝 urllib 默认的客户端标识，这会让守护因与版本无关的原因判定失败并回滚一个正常的版本。预检时状态码不是 200（0 表示没有响应）就停止，报 `preflight failed, nothing changed`，并写明看到的状态码。

`main` 子命令的 `--allow-public-health-failure` 把这一项改为打印一行警告并继续，只用于当前版本已经导致公网健康失败、需要向前发布修复的情况。它不改变守护：切流后公网健康仍须返回 200，否则照常回滚。`rollback` 不做这项预检，当前版本坏掉时正是需要回滚的时候。

## 暂停发布

先替换命令中的配置文件和镜像引用，在部署主机上运行下列命令。

```sh
python3 deploy/sources/deploy.py --config <MAIN_CONFIG> main <IMAGE_REF> --hold-before-switch
python3 deploy/sources/deploy.py --config <MAIN_CONFIG> status
```

命令完成预检、只扩展迁移、资源导出和候选主备就绪检查后，以状态码 `0` 退出并释放发布锁。旧版本继续承接反向代理和共享别名的流量，并持有后台锁。候选主备都是普通 serving 角色，不持后台锁，也不运行全局定时任务。命令列出候选主备的本机 HTTP 入口，可经现有的隧道分别访问。

| 验证入口 | 可以检查的内容 |
| --- | --- |
| 候选主备的预览入口 | 在两个入口分别检查 `/health`、首页、登录页 `/login` 和用户控制台 `/dashboard`。使用合成或专用测试账号登录后，可以检查 API Key 页面 `/keys`、用量页面 `/usage`，以及 `GET /api/v1/auth/me`、`GET /api/v1/keys` 和 `GET /api/v1/usage` 的应答。`GET /api/v1/settings/public` 可用来检查公开设置。 |
| 正式站点的管理入口，由旧后台应答 | 通过正式入口验证管理设置、用户管理和分组（如 `/api/v1/admin/settings`、`/api/v1/admin/users`、`/api/v1/admin/groups`），以及备份、运维实时 WebSocket 和管理 MCP（`/api/v1/mcp`）。直连候选端口请求这些接口会返回 `503`。管理页面即使能加载，其 API 也应通过旧后台验证。 |

共享数据上的少数管理操作允许 serving 处理，例如已登记的钱包配置、余额和渠道监控接口。这些接口仍使用原有的鉴权和共享状态。

候选实例使用共享数据和正常的请求处理逻辑。通过预览入口发起的请求可以写入共享数据或产生真实费用，已受理的异步任务仍由旧后台处理。新版本需兼容仍在运行的旧版本。待执行迁移中包含 `contract` 时，暂停发布会拒绝执行该批迁移，即使传入了 `--allow-contract`。

验证后按需选择恢复或放弃。两个命令使用同一把发布锁。持有暂停记录时，`main` 和 `rollback` 会提示先处理暂停。

```sh
python3 deploy/sources/deploy.py --config <MAIN_CONFIG> resume
# 放弃时运行下列命令。
python3 deploy/sources/deploy.py --config <MAIN_CONFIG> abort
```

- `resume` 先核对候选容器身份、镜像、运行状态、`/health`、网络隔离、旧后台和配置。复检失败会保留暂停，修复后可重试。校验通过后，配置了共享别名时先停止候选主备、重接网络并等它们重新就绪，再使用普通发布的后台交接、切流、守护和退役流程。若重新接入网络失败，`status` 保留失败步骤和原因，可检查目标槽位的容器和网络后人工处理。
- `abort` 按暂停记录的容器 ID 停止并移除候选主备，核实移除后清除暂停记录。已执行的只扩展迁移与已导出的资源保留。清理失败时会显示残留角色和状态，检查后可再次运行 `abort`。若暂停期间人工修改了路由配置，先核实并恢复预期路由，再清理候选实例。

`status` 在 `in_progress.phase=held` 时显示目标槽位、镜像、容器身份、暂停时间和已暂停时长。暂停时长达到 `hold_warning_seconds` 时会提示处理，默认一天。状态保存在本机状态文件，重启后仍可识别。发布只能由 `resume` 继续。

`live_containers` 对每个候选角色显示 `/health` 的返回状态码 `health` 和就绪判定 `ready`。`health` 为 `0` 表示未收到可用响应，为 `null` 表示未探测。容器和镜像身份匹配、`/health` 返回 `200`，且运行时确认是就绪的 serving，`ready` 才为 `true`。暂停中的任一候选未就绪时，`status` 会列出角色，提示先排查或执行 `abort`。

如果发布锁已释放而状态仍停在某个发布步骤，`status` 显示 `phase=interrupted`，`watch` 发出 `release_incomplete` 并带上最后一步。先核对实际路由和容器，再按[人工恢复步骤](#无法自动恢复的情况)处理。`phase=aborting` 表示放弃清理仍待完成。清理中断或已记录失败时，`watch` 发出 `abort_incomplete`，可检查剩余容器后重试 `abort`。

三个入口都接受放在子命令之前的全局 `--dry-run`。`main` 沿用普通发布演练的读操作，包括必要时拉取镜像以及运行一次性检查容器。`resume` 和 `abort` 读取并核对当前状态，输出后续变更命令。演练保留状态、历史、正式容器和路由。

## 自动守护与回滚

切流后检查新 serving 主实例。以下任一情况视为失败（阈值均可在配置中调整）：

- 运行时接口不再报告 `ready`；
- 容器重启或被 OOM 终止；
- 内存超过容器上限的 70%，或 30 秒内上涨超过 4 GiB；
- 公网健康检查连续 3 次失败（失败原因里写明最后一次的状态码，例如 `public health failed 3 times in a row (last status 403)`）；
- Nginx 错误日志里连接新实例端口失败（连接拒绝、upstream 超时）累计达到 10 次。

上游供应商返回的 502、503、429 不算失败：它们在切流前后都可能出现，守护只看 Nginx 能不能连上应用。

守护失败时，脚本立即把 upstream 文件切回上一槽位并 reload，把后台交还旧版本，然后尝试停止新 serving 并**保留**这些容器供排查。若交还后台进入恢复窗口，检查容器、更新重启策略、排空请求和发送 SIGTERM 都只用该窗口的余下时间。`inspect` 失败时用容器列表核实。只有容器状态已确认停止，或列表确认容器已移除，才跳过清理。状态仍无法确认时保留 `in_progress.failed`。

守护期过后的回滚使用 `deploy.py rollback`：它复用上一槽位已停止的容器（不重新创建），按同样的顺序执行启动、后台交接、切流、守护和退役。

守护只能发现切流后几分钟内的问题。常驻监测由 `deploy.py watch`（systemd 单元 `sources-main-watch.service`）负责：每 10 秒对当前版本采样健康状态、重启、OOM、内存和活跃请求数，超过阈值时向 journal 写一条预警。

## 无法自动恢复的情况

如果恢复步骤本身也失败（例如切回旧槽位时 `nginx -t` 失败，或新后台失败后旧后台也无法重新就绪），脚本报告 `FAILED AND NOT RESTORED` 并保留 `in_progress`，原因写在 `in_progress.failed`。此时下一次 `main` 发布会被拒绝，需要人工用 `deploy.py status` 和 `docker ps` 查看现场、恢复服务后再清除该标记。

关闭旧后台自动重启的 Docker 命令返回错误时，更新可能已经生效。除非 Docker 确认容器已移除，工具会先尝试恢复原重启策略并结束此次交接。如果恢复失败，工具会写入 `in_progress.failed`。

发送 SIGTERM 返回失败时，工具在同一个 30 秒窗口内检查 Docker 容器和进程运行态。每次查询都使用窗口内的剩余时间。到期后停止等待查询，丢弃迟到的响应。`draining` 可以由内部排空入口设置。只有容器已退出、已移除或进程通过 `stopping` 报告正在关闭服务，工具才继续交接。若进程仍就绪，工具恢复原重启策略并结束交接。到期仍无法确认时，工具先写入 `in_progress.failed`，再尝试恢复原重启策略并释放发布锁。从修改重启策略前开始，Ctrl-C 不会打断交接的收尾步骤。

SIGTERM 被确认送达后，常规排空和已确认的备份延长期间，`inspect` 和容器列表查询都受当前期限限制。常规期限到达时，工具可再短暂查询备份状态，以发现预检后才启动的备份。查询失败时在同一个恢复窗口内退避重试。只有观察到正在创建的备份，才会按备份期限延长正常交接。

常规期限或已确认的备份期限用尽后，退出确认、恢复重启策略、启动后台、就绪检查和恢复后清理新 serving 共用从该期限起算的 30 秒恢复窗口。切流前，若在恢复窗口内确认旧后台退出，就用原重启策略恢复当前槽位。旧后台排空时收到 Ctrl-C，也会在确认退出后恢复当前槽位。恢复时，更新重启策略和启动后台的 Docker 客户端会继承 SIGINT 屏蔽。如果 Docker 确认旧容器已移除，工具启动已准备好的目标后台。切流失败或守护失败后交还后台时，工具恢复到流量所在槽位。

工具预留最后 5 秒，用来写入 `in_progress.failed`，并在退出状态仍不明确时尝试恢复原重启策略。退出等待和恢复就绪检查都受此预留限制。写入失败记录并完成必要的策略更新后，余下时间仍可用于确认迟到的退出并恢复后台。旧后台恢复成功后，清理新 serving 只使用余下时间。切流失败时删除未接流的新 serving，守护失败时停止并保留新 serving。这两条回退路径也继承交还后台时的恢复截止时间。清理未完成时，旧槽位继续服务，工具保留 `in_progress.failed`，供人工检查目标槽位。恢复期限到达后，工具释放发布锁。若后台未能恢复，需要人工确认持锁进程已退出并恢复当前流量槽位的后台，再清除标记。

## 已知取舍

- 后台交接期间，后台任务暂停到新后台就绪。用户请求照常服务，新的图片任务照常受理，并在新后台起来后执行。支持只读排空的旧后台在关闭监听前仍提供普通管理读接口，关闭监听后到新后台切流前会短暂中断。旧版本可能从排空开始就中断管理读。管理写操作和 MCP 要等新后台就绪，期间返回 503。旧后台上正在进行的长任务（例如定时备份）会延长写操作的等待。
- 守护只覆盖切流后的短时间窗口，较晚出现的问题依赖常驻监测和 serving 的主备结构。
- 只在后台持锁时才执行的分支（应用迁移、以引擎方式打开媒体引擎）无法被 `-check-startup` 覆盖，由后台交接的自动回退兜底。
- 本方案针对单台主机。若以后扩展到多台主机，可以把文件锁换成 PostgreSQL 会话级 advisory lock（连接断开时同样自动释放），其余设计不变。

## Portal

Portal 用同一个工具发布：`deploy.py portal <镜像>`，代码在 `deploy/sources/portal.py`，命令和失败处理见 [deploy/sources/README.md](../../deploy/sources/README.md) 的“Portal”一节。它与 Main 的设计有三点不同。

**一个容器，一段无法避免的不可用。** Portal 的状态目录只有一个写入者：进程先绑定监听地址，再对状态目录加非阻塞文件锁。拿不到锁会立即以代码 1 退出，拿到锁并初始化存储后才开始处理 HTTP 请求。新进程在旧进程释放锁之前无法回答 `/health`。因此不能像 Main 的 serving 那样先启动新实例再切流，从旧 Portal 收到 SIGTERM 到 Nginx 切到新容器之间，Portal 的页面不可用。工具把所有能提前做的事放在发信号之前（拉取镜像、预检、`-check-config` 启动检查、创建新容器），旧进程一退出就启动新容器，每 0.25 秒检查一次，新容器 `/health` 返回 200 就立即切换 Nginx。旧 Portal 收到 SIGTERM 后立即关闭监听并取消在途的只读余额查询，包括同步刷新。取消不会改写余额记录或告警状态。其他已接受的请求和已开始的检测提交或轮询完成后，旧进程才释放状态目录锁并退出。工具从不发送 SIGKILL，Docker 也不会重启被 `docker kill --signal=TERM` 停下的容器，所以信号发出后只能等它退出再启动容器：超过 `exit_timeout`（默认 420 秒）每 30 秒打印警告并继续等待，旧进程一退出就照常继续；超过 `exit_abort_timeout`（默认 3600 秒）才停止，保留 `in_progress`，新容器已创建但未启动、Nginx 未改动，Portal 在旧进程退出前一直不可用，由运维人员在它退出后 `docker start` 旧容器恢复服务再清除 `in_progress`。当前容器在交接时已经不在运行（例如崩溃）则不发信号，直接启动目标容器，所以 `portal-rollback` 在当前 Portal 崩溃时同样可用。交接到守护之间的命令超时、命令无法执行和 Ctrl-C 中断都按失败处理：先回退到旧容器，再以错误结束。

**应用提供的支持。** Portal 只有 `GET /health`（200 `{"status":"ok"}` 或 503），没有 Main 的运行时接口、角色、令牌和排空。新镜像提供 `/app/sources-portal -check-config`：只读的启动检查，不取锁、不写任何东西、不打开监听端口，校验环境变量和磁盘上的状态，成功时输出 `SOURCES_PORTAL_CONFIG_OK` 并以 0 退出，失败时输出一行错误并以 1 退出。工具用真实的环境和挂载（全部强制只读）运行它，在碰旧容器之前就发现配置错误。没有该参数的旧镜像会按正常启动处理、拿不到锁而失败，工具同样视为检查失败。

**固定结构。** 两个槽位 A、B 轮流使用，容器名为 `<前缀>-{a,b}`，每个槽位的本机端口在 `portal.json` 中固定；Nginx 只引用固定的 `upstream sources_portal`，切流时只重写这个 upstream 文件（与 Main 相同的“写入、`nginx -t`、失败恢复原文件、成功 reload”顺序）。首次接入用 `portal-adopt` 记录运行中的容器（槽位 `legacy`，工具从不删除它）。交接后任何失败都按“停新容器（它持有锁）→ 启动旧容器并等 `/health` → 如已切流则切回”回退；回退本身失败时报告 `FAILED AND NOT RESTORED` 并保留 `in_progress`。`portal-rollback` 用同样的流程切回上一容器，但较旧的 Portal 可能拒绝较新版本写下的状态，此时自动回到当前版本。

Portal 和 Main 共用一把发布锁（`portal.json` 与 `main.json` 的 `lock_file` 是同一个文件），两者的发布不会重叠。

**切流后的检查与状态。** Nginx reload 返回时旧 worker 可能仍在接受连接。Portal 在切流阶段先等公网健康返回 200，成功响应后按等待开始时的启动时间和重启次数复核容器，确认仍在运行、未处于重启中且没有被 OOM 终止，再开始完整守护时长与失败计数；等待复用 `ready_timeout`，期间新容器停止、重启（包括探测返回 200 之前发生的重启）、被 OOM 终止或等待超时，均按原流程回退。`portal-status` 在发布进行中把 `current`、`previous` 标为本次发布之前的记录，并在独立的 `target` 项展示目标容器的实时状态，守护阶段可直接查看正在服务的目标；已停止的容器不显示过期的健康状态。
