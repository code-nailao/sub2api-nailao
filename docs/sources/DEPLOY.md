# 发布与部署

本文说明本仓库的主站（Main）如何从一个镜像发布到单台 Docker 主机：为什么这样设计、应用为此提供了什么、发布脚本按什么顺序执行、每一步失败后留下什么。工具本身的用法见 [deploy/sources/README.md](../../deploy/sources/README.md)，代码在 `deploy/sources/deploy.py`。

## 目标

- **一条命令发布**：`deploy.py main <镜像>` 完成预检、迁移、启动新实例、后台交接、切流、自动守护和退役旧实例，中间无需人工操作。
- **用户请求不中断**：已建立的流式连接和已受理的异步任务不被截断。
- **可回滚**：守护期内发现问题自动回滚；守护期后一条命令回到上一版本。
- **工具不随版本改动**：连续发布不需要修改发布脚本或 Nginx 配置。

## 构建

打 `v*` tag 后，`.github/workflows/release.yml` 从固定提交构建：`scripts/sources_release/build.sh` 要求工作树干净，使用锁定的依赖构建前端、Portal 和后端；`ci_gate.py` 核对该提交的 CI 结果；`publish.py` 只发布一次镜像，已发布的摘要不覆盖。部署时按摘要引用镜像。

## 为什么用固定槽位

如果容器名、端口和 Nginx upstream 名都带版本号，每次发布都要新开端口、改写多处 Nginx 引用、给静态资源接一段新的兜底链，发布脚本也就要随版本修改。因此改为固定的结构：

- **两个槽位 A、B 轮流使用。** 每个槽位三个容器：serving 主、serving 备和 background。容器名固定为 `<前缀>-{a,b}-{serving,standby,background}`，每个槽位的端口在配置里固定。
- **新版本总是发到“非当前”槽位。** 那里原有的容器是上上个版本，发布时直接删除重建；上一个版本留在另一个槽位，停止后保留，用于回滚。所以任何时候只保留一个可回滚的上一版本。
- **Nginx 只引用两个固定 upstream 名**：`sources_main_serving`（主 + 备，备用 `backup`）和 `sources_main_admin`（后台）。切流时只重写一个由脚本生成的 upstream 文件，其他 Nginx 配置不再变化。预检会拒绝仍在引用按版本命名的 upstream 的配置。
- **静态资源放在一个固定目录。** 文件名带内容哈希，新版本的资源追加复制进去，不删除也不覆盖，所以切换后仍停留在旧页面的浏览器能继续加载旧资源。
- **内部调用方使用固定别名。** 每个 serving 容器在所有网络上带同一个网络别名（默认 `sources-main-serving`），后台容器没有。旧版本退役后自动从该名字的解析结果中消失，内部服务（如 Portal）不会被绑在某个旧容器的地址上。
- 服务器上只有一个状态文件记录当前槽位、上一槽位、镜像和进行中的步骤；每次正式运行在 `history.jsonl` 追加一行结果和各步骤耗时，演练（`--dry-run`）不写历史。

## 进程角色与唯一后台

同一个镜像以两种角色运行，由环境变量 `SOURCES_PROCESS_ROLE` 区分：

- **serving**：处理用户和 API 请求，不运行后台任务。主、备两个实例同时就绪，主实例故障时 Nginx 自动转到备实例。
- **background**：运行全部后台服务（定时任务、渠道监控、OAuth 刷新、媒体引擎等）并处理需要它们的管理接口。

同一时刻只能有一个后台。这由操作系统文件锁保证：background 在构造任何依赖之前对锁目录中的 `native-background.lock` 加 `flock`，媒体引擎存储在打开时再取一把自己的锁。进程退出时内核自动释放锁，所以新后台只有在旧后台真正退出后才能拿到锁。发布脚本只负责安排顺序，不需要证明“没有两个后台”，也从不发送 SIGKILL。

每个实例通过内部接口 `/internal/sources/runtime` 报告角色、`ready` 和 `owns_background`；`/internal/sources/drain` 让 serving 实例进入排空状态。两个接口都需要运行令牌。background 还报告 `admin_during_drain`（值为 `read-only`，表示排空期间管理接口只读，见下节）、`active_admin_writes`（仍在处理的非只读管理请求数）和 `stopping`（尚未停完的后台服务）。对 background 调用 `/internal/sources/drain` 同样会让它进入只读排空，直到进程退出；发布工具只对 serving 调用这个接口。

## 应用为发布提供的支持

- **后台优雅退出。** serving 和 standalone 收到 SIGTERM 后先关闭 HTTP，等在途请求结束，再停止各项服务后退出，顺序不变。background 不同，它在停止后台服务的整个过程中保持监听，让管理页面在交接期间继续可用：
  1. 进入只读排空：管理接口只应答 `GET` 和 `HEAD`。其它方法、MCP（`/api/v1/mcp`）、WebSocket 升级，以及少数 `GET`——媒体引擎审阅（它读的存储会在第 3 步关闭）和会访问上游供应商的查询（账号用量的主动查询、刷新余额、OpenAI/Grok/国内供应商额度与余额、Claude 重置额度、账号模型列表；它们会探测上游、可能刷新并保存 OAuth 凭据、写账号状态或启动超出请求的后台工作，清单在 `processrole/handoff.go`）——在进入处理器之前返回 503，使用原生错误信封（`reason` 为 `BACKGROUND_HANDOFF_READ_ONLY`，`message` 说明正在发版、暂时只读、请稍后重试），带 `Retry-After: 5`。请求没有执行任何部分，所以重试总是安全的。只读是因为写请求可能把工作交给已经停止的服务，或启动进程退出时会被截断的 goroutine。
  2. 等 SIGTERM 之前已经进入的非只读管理请求处理完，与原来“先等在途请求、再停服务”的顺序一致。
  3. 并行停止所有后台服务（下面各项的语义不变）。
  4. 结束打开着的管理 WebSocket：取消它们的请求上下文，运维实时页发送关闭帧后自动重连。否则被劫持的连接不会随 HTTP 关闭而结束，会一直拖住进程退出。
  5. 关闭 HTTP 监听，等在途读请求结束，停止其余服务（用量、计费缓存、OAuth、日志等）和 Redis、数据库连接，退出。锁仍然只在进程退出时由内核释放。

  排空期间 `/health` 照常返回 200：进程仍在应答管理读请求。是否就绪以运行时接口为准：排空时 `ready` 为 false、`draining` 为 true。常驻监测和巡检读 `/health` 时，这段时间不会被当作故障。

  各后台服务停止时：
  - OAuth 刷新停止时不再发起新的刷新，但不取消已经在和供应商通信的刷新，等它们保存新凭据后再返回（单次刷新有超时上限）。否则供应商已轮换 refresh token 而新凭据被丢弃，账号下次刷新会失败。
  - 渠道探测和定时测试停止时立即取消在途探测；被取消的探测不写历史，避免交接产生假的“失败”记录。
  - 媒体引擎只等已领取的操作完成；新任务留在共享存储中，由下一个后台领取。提交结果不明的任务标为 unknown，不重发。
  - 定时备份最多等 5 分钟，让正在进行的备份及其过期备份清理做完，超时就取消。所以在定时备份进行时发版，这次备份会被取消，交接期间写操作也要多等最多 5 分钟（读不受影响）。发版应避开定时备份时段。
- **一次性命令**（`backend/cmd/server/sources_deploy_commands.go`）。它们都不监听端口、不取后台锁、不启动后台服务，并且只输出一行带固定前缀的结果供脚本读取：
  - `-list-pending-migrations`：只读迁移账本，输出 `SOURCES_PENDING_MIGRATIONS a.sql,b.sql`，供 `-migrate-only` 使用。
  - `-check-startup`：用 serving 语义、临时锁目录和临时令牌，按生产配置构造全部依赖后退出，输出 `SOURCES_STARTUP_CHECK_OK {...}`。有待执行迁移时会失败，所以脚本先迁移再检查。
  - `-export-web-assets <目录>`：把镜像内嵌的前端资源复制到指定目录（只追加、不覆盖），保证 HTML 与资源来自同一次构建。
- **只扩展的迁移。** 新迁移在旧版本仍在服务时执行，所以只能新增表、可空或带默认值的列和索引。`deploy/sources/migration_lint.py` 在 CI 中拒绝删除表或列、改名、改列类型、`SET NOT NULL` 和 `TRUNCATE`，除非文件名包含 `contract`；经审查的例外（例如原版同步带来的语句）登记在 `deploy/sources/migration-allow.txt` 并写明原因。带 `contract` 的迁移只有加 `--allow-contract` 才会执行。

## 发布顺序

整个命令持有发布锁，防止并发发布。上一次运行没有走完（状态里 `in_progress` 不为空）时，新的发布会拒绝执行，需要先人工确认现场。

| 步骤 | 内容 | 失败时留下什么 |
| --- | --- | --- |
| 拉取镜像 | 本地没有时按引用拉取 | 现场不变 |
| 预检 | Nginx 已使用固定 upstream；目标槽位不是当前槽位、没有仍在排空的容器；目标端口可绑定且（落在临时端口范围时）已被保留；宿主可用内存足够；用守护阶段完全相同的请求访问公网健康地址，必须返回 200；用新镜像列出待执行迁移；有 `contract` 迁移而未加参数则拒绝 | 现场不变，没有创建任何容器 |
| 迁移 | 有待执行迁移时，用新镜像以 background 环境执行 `-migrate-only` | 退出；迁移只扩展结构，旧版本继续服务 |
| 启动检查 | 分别用 serving 和 background 两套环境运行 `-check-startup`，两套环境的配置错误都在这里暴露 | 退出，没有创建 serving 容器；已执行的迁移保留（旧版本兼容） |
| 导出静态资源 | `-export-web-assets` 导出到临时目录，再追加进固定资源目录 | 退出；资源目录只多了新文件 |
| 启动新 serving | 删除目标槽位的旧容器，创建并启动主、备两个 serving，等待就绪 | 删除新 serving 容器，退出；旧版本继续服务 |
| 后台交接 | 旧后台改为不自动重启，发送一次 SIGTERM，等它处理完在途任务后自行退出；然后启动新后台，等待 `ready` 且 `owns_background`。发信号前日志写明旧后台排空期间管理接口是只读还是不可用（旧版本不报告 `admin_during_drain`，那一次仍不可用）；等待期间 SIGTERM 后约 5 秒、之后每分钟写一次它仍在停止的服务。交接中每 0.5 秒检查一次 | 新后台在超时内未就绪或容器退出：停止新后台，重新启动旧后台，删除新 serving，退出。旧后台在 `background_exit_timeout`（默认 2100 秒）内没有退出：`FAILED AND NOT RESTORED`，见“无法自动恢复的情况” |
| 切流 | 生成新的 upstream 文件，`nginx -t` 通过后 reload 一次；旧 worker 继续服务已建立的连接直到结束 | `nginx -t` 失败：恢复原文件，后台交还旧版本，删除新 serving，退出 |
| 守护 | 默认 5 分钟、每 10 秒检查一次（见下节） | 自动回滚（见下节） |
| 退役 | 旧 serving 改为不自动重启，发起排空，再发送 SIGTERM，不等待；它处理完已转来的请求（包括流式连接）后自行退出。更新状态文件，追加历史 | — |

`--dry-run` 是全局参数，写在子命令之前（`deploy.py --dry-run main <镜像>`）。它只打印会执行的变更命令；只读步骤（列出迁移、启动检查）照常执行。有待执行迁移时，演练不会执行迁移，而启动检查拒绝带待执行迁移的数据库，所以演练跳过启动检查并在输出中写明；两个环境的配置要到正式运行时，在迁移之后、创建任何容器之前才第一次校验。公网健康检查是只读请求，演练同样会执行，所以演练能发现守护阶段必然失败的公网检查。失败的演练没有改变任何东西，不在 `history.jsonl` 留下记录，以免和失败的正式发布混淆。

### 公网健康预检

公网健康地址（`main.json` 的 `public_health_url`）在切流前后用同一个请求检查。所有请求都带固定的 `User-Agent`：公网入口前的部分边缘防护会拒绝 urllib 默认的客户端标识，这会让守护因与版本无关的原因判定失败并回滚一个正常的版本。预检时状态码不是 200（0 表示没有响应）就停止，报 `preflight failed, nothing changed`，并写明看到的状态码。

`main` 子命令的 `--allow-public-health-failure` 把这一项改为打印一行警告并继续，只用于当前版本已经导致公网健康失败、需要向前发布修复的情况。它不改变守护：切流后公网健康仍须返回 200，否则照常回滚。`rollback` 不做这项预检，当前版本坏掉时正是需要回滚的时候。

## 自动守护与回滚

切流后检查新 serving 主实例。以下任一情况视为失败（阈值均可在配置中调整）：

- 运行时接口不再报告 `ready`；
- 容器重启或被 OOM 终止；
- 内存超过容器上限的 70%，或 30 秒内上涨超过 4 GiB；
- 公网健康检查连续 3 次失败（失败原因里写明最后一次的状态码，例如 `public health failed 3 times in a row (last status 403)`）；
- Nginx 错误日志里连接新实例端口失败（连接拒绝、upstream 超时）累计达到 10 次。

上游供应商返回的 502、503、429 不算失败：它们在切流前后都可能出现，守护只看 Nginx 能不能连上应用。

守护失败时，脚本立即把 upstream 文件切回上一槽位并 reload，把后台交还旧版本，然后停止新 serving 并**保留**这些容器供排查。

守护期过后的回滚使用 `deploy.py rollback`：它复用上一槽位已停止的容器（不重新创建），按同样的顺序执行启动、后台交接、切流、守护和退役。

守护只能发现切流后几分钟内的问题。常驻监测由 `deploy.py watch`（systemd 单元 `sources-main-watch.service`）负责：每 10 秒对当前版本采样健康状态、重启、OOM、内存和活跃请求数，超过阈值时向 journal 写一条预警。

## 无法自动恢复的情况

如果恢复步骤本身也失败（例如切回旧槽位时 `nginx -t` 失败，或新后台失败后旧后台也无法重新就绪），脚本报告 `FAILED AND NOT RESTORED` 并保留 `in_progress`，原因写在 `in_progress.failed`。此时下一次发布会被拒绝，需要人工用 `deploy.py status` 和 `docker ps` 查看现场、恢复服务后再清除该标记。

旧后台在 `background_exit_timeout` 内没有退出也属于这种情况。工具没有杀任何进程，新后台已创建但没有启动，Nginx 没有改动。旧后台仍在排空，管理读接口仍由它应答；但它已设为不自动重启，Docker 也不会重启被 `docker kill` 停下的容器，所以它退出后就没有后台进程了。`deploy.py status` 里它的 `status` 为 `running`、`restart_policy` 为 `no`。处理方法：等它退出（`docker ps -a` 看状态，`docker logs` 看它在等什么），然后 `docker update --restart=unless-stopped <旧后台容器>` 和 `docker start <旧后台容器>`，用 `status` 确认它重新运行，再清除 `in_progress`。在此之前不要再次发布。

## 已知取舍

- 后台交接期间，后台任务暂停到新后台就绪；用户请求不受影响，新的图片任务照常受理并在新后台起来后执行。管理读接口在旧后台排空期间照常可用，只在“旧后台关闭监听到新后台就绪并切流”这几秒不可用；管理写操作和 MCP 要等新后台就绪，期间返回 503。旧后台上正在进行的长任务（例如定时备份）只延长写操作的等待。
- 守护只覆盖切流后的短时间窗口，较晚出现的问题依赖常驻监测和 serving 的主备结构。
- 只在后台持锁时才执行的分支（应用迁移、以引擎方式打开媒体引擎）无法被 `-check-startup` 覆盖，由后台交接的自动回退兜底。
- 本方案针对单台主机。若以后扩展到多台主机，可以把文件锁换成 PostgreSQL 会话级 advisory lock（连接断开时同样自动释放），其余设计不变。

## Portal

Portal 用同一个工具发布：`deploy.py portal <镜像>`，代码在 `deploy/sources/portal.py`，命令和失败处理见 [deploy/sources/README.md](../../deploy/sources/README.md) 的“Portal”一节。它与 Main 的设计有三点不同。

**一个容器，一段无法避免的不可用。** Portal 的状态目录只有一个写入者：进程启动时对状态目录加非阻塞文件锁，第二个进程拿不到锁会立即以代码 1 退出；监听端口在锁和全部存储初始化之后才打开，所以新进程在旧进程退出之前无法回答 `/health`。因此不能像 Main 的 serving 那样先启动新实例再切流，从旧 Portal 收到 SIGTERM 到 Nginx 切到新容器之间，Portal 的页面不可用。工具把所有能提前做的事放在发信号之前（拉取镜像、预检、`-check-config` 启动检查、创建新容器），旧进程一退出就启动新容器，每 0.25 秒检查一次，新容器 `/health` 返回 200 就立即切换 Nginx。旧 Portal 收到 SIGTERM 后立即关闭监听，处理完在途请求后退出（通常几秒，极少数同步余额刷新最长约 375 秒）。工具从不发送 SIGKILL，Docker 也不会重启被 `docker kill --signal=TERM` 停下的容器，所以信号发出后只能等它退出再启动容器：超过 `exit_timeout`（默认 420 秒）每 30 秒打印警告并继续等待，旧进程一退出就照常继续；超过 `exit_abort_timeout`（默认 3600 秒）才停止，保留 `in_progress`，新容器已创建但未启动、Nginx 未改动，Portal 在旧进程退出前一直不可用，由运维人员在它退出后 `docker start` 旧容器恢复服务再清除 `in_progress`。当前容器在交接时已经不在运行（例如崩溃）则不发信号，直接启动目标容器，所以 `portal-rollback` 在当前 Portal 崩溃时同样可用。交接到守护之间的命令超时、命令无法执行和 Ctrl-C 中断都按失败处理：先回退到旧容器，再以错误结束。

**应用提供的支持。** Portal 只有 `GET /health`（200 `{"status":"ok"}` 或 503），没有 Main 的运行时接口、角色、令牌和排空。新镜像提供 `/app/sources-portal -check-config`：只读的启动检查，不取锁、不写任何东西、不打开监听端口，校验环境变量和磁盘上的状态，成功时输出 `SOURCES_PORTAL_CONFIG_OK` 并以 0 退出，失败时输出一行错误并以 1 退出。工具用真实的环境和挂载（全部强制只读）运行它，在碰旧容器之前就发现配置错误。没有该参数的旧镜像会按正常启动处理、拿不到锁而失败，工具同样视为检查失败。

**固定结构。** 两个槽位 A、B 轮流使用，容器名为 `<前缀>-{a,b}`，每个槽位的本机端口在 `portal.json` 中固定；Nginx 只引用固定的 `upstream sources_portal`，切流时只重写这个 upstream 文件（与 Main 相同的“写入、`nginx -t`、失败恢复原文件、成功 reload”顺序）。首次接入用 `portal-adopt` 记录运行中的容器（槽位 `legacy`，工具从不删除它）。交接后任何失败都按“停新容器（它持有锁）→ 启动旧容器并等 `/health` → 如已切流则切回”回退；回退本身失败时报告 `FAILED AND NOT RESTORED` 并保留 `in_progress`。`portal-rollback` 用同样的流程切回上一容器，但较旧的 Portal 可能拒绝较新版本写下的状态，此时自动回到当前版本。

Portal 和 Main 共用一把发布锁（`portal.json` 与 `main.json` 的 `lock_file` 是同一个文件），两者的发布不会重叠。
