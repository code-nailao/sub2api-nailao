# 发布与部署

本文说明本仓库的主站（Main）如何从一个镜像发布到单台 Docker 主机：为什么这样设计、应用为此提供了什么、发布脚本按什么顺序执行、每一步失败后留下什么。工具本身的用法见 [deploy/sources/README.md](../../deploy/sources/README.md)，代码在 `deploy/sources/deploy.py`。

## 目标

- **一条命令发布**：`deploy.py main <镜像>` 完成预检、迁移、启动新实例、后台交接、切流、自动守护和退役旧实例，中间无需人工操作。
- **用户请求不中断**：已建立的流式连接和已受理的异步任务不被截断。
- **可回滚**：守护期内发现问题自动回滚；守护期后一条命令回到上一版本。
- **工具不随版本改动**：连续发布不需要修改发布脚本或 Nginx 配置。

## 构建

打 `v*` tag 后，`.github/workflows/release.yml` 从固定提交构建：`scripts/sources_release/build.sh` 要求工作树干净，使用锁定的依赖构建前端、Portal 和后端；`ci_gate.py` 核对该提交的 CI 结果；`publish.py` 只发布一次镜像，已发布的摘要不覆盖。部署时按摘要引用镜像。

## 为什么用固定槽位

如果容器名、端口和 Nginx upstream 名都带版本号，每次发布都要新开端口、改写多处 Nginx 引用、给静态资源接一段新的兜底链，发布脚本也就要随版本修改。因此改为固定的结构：

- **两个槽位 A、B 轮流使用。** 每个槽位三个容器：serving 主、serving 备和 background。容器名固定为 `<前缀>-{a,b}-{serving,standby,background}`，每个槽位的端口在配置里固定。
- **新版本总是发到“非当前”槽位。** 那里原有的容器是上上个版本，发布时直接删除重建；上一个版本留在另一个槽位，停止后保留，用于回滚。所以任何时候只保留一个可回滚的上一版本。
- **Nginx 只引用两个固定 upstream 名**：`sources_main_serving`（主 + 备，备用 `backup`）和 `sources_main_admin`（后台）。切流时只重写一个由脚本生成的 upstream 文件，其他 Nginx 配置不再变化。预检会拒绝仍在引用按版本命名的 upstream 的配置。
- **静态资源放在一个固定目录。** 文件名带内容哈希，新版本的资源追加复制进去，不删除也不覆盖，所以切换后仍停留在旧页面的浏览器能继续加载旧资源。
- **内部调用方使用固定别名。** 每个 serving 容器在所有网络上带同一个网络别名（默认 `sources-main-serving`），后台容器没有。旧版本退役后自动从该名字的解析结果中消失，内部服务（如 Portal）不会被绑在某个旧容器的地址上。
- Main 状态文件记录当前槽位、上一槽位、镜像和进行中的步骤。历史文件记录发布结果与耗时。追加历史失败时只告警一次，命令结果以状态和操作结果为准。演练（`--dry-run`）不写历史。

## 进程角色与唯一后台

同一个镜像以两种角色运行，由环境变量 `SOURCES_PROCESS_ROLE` 区分：

- **serving**：处理用户和 API 请求，不运行后台任务。主、备两个实例同时就绪，主实例故障时 Nginx 自动转到备实例。
- **background**：运行全部后台服务（定时任务、渠道监控、OAuth 刷新、媒体引擎等）并处理需要它们的管理接口。

操作系统文件锁保证同一时刻**最多一个后台持有者**。background 在构造依赖前对 `native-background.lock` 加 `flock`，媒体引擎打开存储时再取得自己的锁。旧进程退出后内核释放锁，新后台启动并取得锁前会有交接空档。排空超时或恢复失败时，空档可能持续到人工恢复。

每个实例通过内部接口 `/internal/sources/runtime` 报告角色、`ready` 和 `owns_background`；`/internal/sources/drain` 让 serving 实例进入排空状态。两个接口都需要运行令牌。background 还报告 `admin_during_drain`（值为 `read-only`，表示排空期间管理接口只读，见下节）、`active_admin_writes`（排空期间会被拒绝、仍在处理的管理请求数）和 `stopping`（尚未停完的后台服务）。对 background 调用 `/internal/sources/drain` 同样会让它进入只读排空，直到进程退出；发布工具只对 serving 调用这个接口。

## 应用为发布提供的支持

- **后台优雅退出。** serving 和 standalone 收到 SIGTERM 后先关闭 HTTP，等在途请求结束，再停止各项服务后退出，顺序不变。background 不同，它在停止后台服务的整个过程中保持监听，让管理页面在交接期间继续可用：
  1. 进入只读排空：管理接口只应答 `GET` 和 `HEAD`。其它方法、MCP（`/api/v1/mcp`）、WebSocket 升级，以及少数 `GET`——媒体引擎审阅（它读的存储会在第 3 步关闭）和会访问上游供应商的查询（账号用量的主动查询、刷新余额、OpenAI/Grok/国内供应商额度与余额、Claude 重置额度、账号模型列表；它们会探测上游、可能刷新并保存 OAuth 凭据、写账号状态或启动超出请求的后台工作，清单在 `processrole/handoff.go`）——在进入处理器之前返回 503，使用原生错误信封（`reason` 为 `BACKGROUND_HANDOFF_READ_ONLY`，`message` 说明正在发版、暂时只读、请稍后重试），带 `Retry-After: 5`。请求没有执行任何部分，所以重试总是安全的。只读是因为写请求可能把工作交给已经停止的服务，或启动进程退出时会被截断的 goroutine。
  2. 等 SIGTERM 之前已经进入、排空期间会被拒绝的管理请求（写、MCP、上面那些会访问上游的查询；WebSocket 除外）处理完，与原来“先等在途请求、再停服务”的顺序一致。
  3. 并行停止所有后台服务（下面各项的语义不变）。
  4. 结束打开着的管理 WebSocket：取消它们的请求上下文，运维实时页发送关闭帧后自动重连。否则被劫持的连接不会随 HTTP 关闭而结束，会一直拖住进程退出。
  5. 关闭 HTTP 监听，等在途读请求结束，停止其余服务（用量、计费缓存、OAuth、日志等）和 Redis、数据库连接，退出。锁仍然只在进程退出时由内核释放。

  管理界面与 API 同源部署时浏览器不发 CORS 预检；如果跨源部署，排空期间的 `OPTIONS` 预检同样得到不带 CORS 头的 503，浏览器会把它当作网络错误显示。

  排空期间 `/health` 照常返回 200：进程仍在应答管理读请求。是否就绪以运行时接口为准：排空时 `ready` 为 false、`draining` 为 true。常驻监测和巡检读 `/health` 时，这段时间不会被当作故障。

  各后台服务停止时：
  - OAuth 刷新停止时不再发起新的刷新，但不取消已经在和供应商通信的刷新，等它们保存新凭据后再返回（单次刷新有超时上限）。否则供应商已轮换 refresh token 而新凭据被丢弃，账号下次刷新会失败。
  - 渠道探测和定时测试停止时立即取消在途探测；被取消的探测不写历史，避免交接产生假的“失败”记录。
  - 媒体引擎只等已领取的操作完成；新任务留在共享存储中，由下一个后台领取。提交结果不明的任务标为 unknown，不重发。
  - 定时备份最多等 5 分钟，让正在进行的备份及其过期备份清理做完，超时就取消。所以在定时备份进行时发版，这次备份会被取消，交接期间写操作也要多等最多 5 分钟（读不受影响）。发版应避开定时备份时段。
- **一次性命令**（`backend/cmd/server/sources_deploy_commands.go`）。它们都不监听端口、不取后台锁、不启动后台服务，并且只输出一行带固定前缀的结果供脚本读取：
  - `-list-pending-migrations`：只读迁移账本，输出 `SOURCES_PENDING_MIGRATIONS a.sql,b.sql`，供 `-migrate-only` 使用。
  - `-check-startup`：用 serving 语义、临时锁目录和临时令牌，按生产配置构造全部依赖后退出，输出 `SOURCES_STARTUP_CHECK_OK {...}`。有待执行迁移时会失败，所以脚本先迁移再检查。
  - `-export-web-assets <目录>`：把镜像内嵌的前端资源复制到指定目录（只追加、不覆盖），保证 HTML 与资源来自同一次构建。
- **只扩展的迁移。** 新迁移在旧版本仍在服务时执行，所以只能新增表、可空或带默认值的列和索引。`deploy/sources/migration_lint.py` 在 CI 中拒绝删除表或列、改名、改列类型、`SET NOT NULL` 和 `TRUNCATE`，除非文件名包含 `contract`；经审查的例外（例如原版同步带来的语句）登记在 `deploy/sources/migration-allow.txt` 并写明原因。带 `contract` 的迁移只有加 `--allow-contract` 才会执行。

## 发布顺序

所有 Main 写入入口都先取得发布锁，再读取发布状态。`in_progress` 非空时，`main`、`rollback` 和 `adopt` 会拒绝执行。`adopt` 检查现有配置引用的状态文件和目标工作目录的状态文件。按状态的 `phase` 选择继续、放弃或人工恢复，见“暂停发布”。

| 步骤 | 内容 | 失败时留下什么 |
| --- | --- | --- |
| 拉取镜像 | 本地没有时按引用拉取 | 现场不变 |
| 预检 | Nginx 已使用固定 upstream；目标槽位不是当前槽位、没有仍在排空的容器；目标端口可绑定且（落在临时端口范围时）已被保留；宿主可用内存足够；用守护阶段完全相同的请求访问公网健康地址，必须返回 200；用新镜像列出待执行迁移；有 `contract` 迁移而未加参数则拒绝 | 现场不变，没有创建任何容器 |
| 迁移 | 有待执行迁移时，用新镜像以 background 环境执行 `-migrate-only` | 退出；迁移只扩展结构，旧版本继续服务 |
| 启动检查 | 分别用 serving 和 background 两套环境运行 `-check-startup`，两套环境的配置错误都在这里暴露 | 退出，没有创建 serving 容器；已执行的迁移保留（旧版本兼容） |
| 导出静态资源 | `-export-web-assets` 导出到临时目录，再追加进固定资源目录 | 退出；资源目录只多了新文件 |
| 启动新 serving | 删除目标槽位的旧容器，创建并启动主、备两个 serving，等待就绪 | 排空并移除本次创建的 serving，旧版本继续服务。清理失败时保留故障状态 |
| 后台交接 | 旧后台改为不自动重启，发送一次 SIGTERM，等它处理完在途任务后自行退出；然后启动新后台，等待 `ready` 且 `owns_background`。发信号前日志写明旧后台排空期间管理接口是只读还是不可用（旧版本不报告 `admin_during_drain`，那一次仍不可用）；等待期间 SIGTERM 后约 5 秒、之后每分钟写一次它仍在停止的服务。交接中每 0.5 秒检查一次 | 新后台在超时内未就绪或容器退出：停止新后台，重新启动旧后台，排空并移除新 serving。旧后台在 `background_exit_timeout`（默认 2100 秒）内没有退出：`FAILED AND NOT RESTORED`，见“无法自动恢复的情况” |
| 切流 | 生成新的 upstream 文件，`nginx -t` 通过后 reload 一次；旧 worker 继续服务已建立的连接直到结束 | `nginx -t` 或 reload 失败时尝试恢复原文件和旧路由，确认旧路由后交还后台。恢复完成后排空并移除新 serving |
| 守护 | 默认 5 分钟、每 10 秒检查一次（见下节） | 自动回滚（见下节） |
| 退役 | 旧 serving 改为不自动重启，发起排空，再发送 SIGTERM，不等待；它处理完已转来的请求（包括流式连接）后自行退出。更新状态文件，追加历史 | — |

`--dry-run` 是全局参数，写在子命令之前（`deploy.py --dry-run main <镜像>`）。演练按需拉取镜像，并实际运行用于列出迁移和检查启动的一次性容器。迁移、资源导出、正式发布容器变更和 Nginx reload 只打印计划。有待执行迁移时，演练不会执行迁移，而启动检查拒绝带待执行迁移的数据库，所以演练跳过启动检查并在输出中写明；两个环境的配置要到正式运行时，在迁移之后、创建任何容器之前才第一次校验。公网健康检查是只读请求，演练同样会执行，所以演练能发现守护阶段必然失败的公网检查。演练不在 `history.jsonl` 留下记录。

### 公网健康预检

公网健康地址（`main.json` 的 `public_health_url`）在切流前后用同一个请求检查。所有请求都带固定的 `User-Agent`：公网入口前的部分边缘防护会拒绝 urllib 默认的客户端标识，这会让守护因与版本无关的原因判定失败并回滚一个正常的版本。预检时状态码不是 200（0 表示没有响应）就停止，报 `preflight failed, nothing changed`，并写明看到的状态码。

`main` 子命令的 `--allow-public-health-failure` 把这一项改为打印一行警告并继续，只用于当前版本已经导致公网健康失败、需要向前发布修复的情况。它不改变守护：切流后公网健康仍须返回 200，否则照常回滚。`rollback` 不做这项预检，当前版本坏掉时正是需要回滚的时候。

## 暂停发布

需要先体验新版本时，在部署主机上使用以下入口；尖括号全部替换为自己的配置或镜像引用：

```sh
python3 deploy/sources/deploy.py --config <MAIN_CONFIG> main <IMAGE_DIGEST> --hold-before-switch
python3 deploy/sources/deploy.py --config <MAIN_CONFIG> status
python3 deploy/sources/deploy.py --config <MAIN_CONFIG> resume
# 或者放弃本次发布
python3 deploy/sources/deploy.py --config <MAIN_CONFIG> abort
```

`main --hold-before-switch` 照常拉取、预检、执行只扩展迁移、检查启动配置、追加资源、启动目标 serving 和 standby，等它们就绪后以成功退出。旧后台没有收到信号，Nginx 文件没有改动，旧版本继续服务正式流量。暂停实例没有共享的 `serving_alias`，因此内部调用方也不会通过稳定别名提前找到新版本；每个实例自己的网络名称仍可访问。工具输出它们各自的本机 HTTP 入口，负责人使用已有的隧道工具分别转发到自己的本机，浏览器和请求工具访问转发后的入口，不把端口暴露到公网。暂停不能与待执行的 `contract` 迁移一起使用，即使加了 `--allow-contract` 也会拒绝。

Main 的状态集中在 `in_progress`。空闲时该字段为 `null`。其它阶段如下。

| `phase` | 含义 |
| --- | --- |
| `deploying` | 工具正在发布，`step` 记录当前步骤。发布进程已退出但状态仍停在这里时需要核查 |
| `held` | 新实例已就绪，等待人工验证。状态记录目标槽位、镜像和容器 ID、`held_at`、当前版本快照及配置和 upstream 指纹 |
| `aborting` | 正在放弃，或上次清理未完成。再次运行 `abort` 可接着清理 |
| `failed` | 自动恢复未完成。`failed_step` 和 `reason` 记录失败位置和原因 |

准备新槽位时会移除留在该槽位的旧容器。工具确认目标槽位清理完毕才开始创建暂停实例。暂停和普通发布都复用这两个槽位。即使 `hold` 后成功 `abort`，`previous` 记录所指的回滚容器也可能已经不存在。

暂停命令退出时释放发布锁。暂停不会自动过期。`status` 展示暂停时长、容器状态和身份核对结果，超过 `hold_warning_seconds` 时提示负责人处理。暂停期间 `main` 和 `rollback` 会提示先 `resume` 或 `abort`，这两个入口也使用同一把发布锁。旧格式的 Main 暂停或故障记录可以直接读取。

### 暂停实例的共享状态边界

暂停实例是普通 serving，**不是只读沙箱**。`backend/internal/processrole/role.go` 的 `acquireOwner` 不给 serving 取后台锁，`StartBackground` 不启动全局定时服务；`backend/internal/service/sources_media_engine.go` 使用 producer，旧后台仍是任务执行者。`extensions/sources-media-engine/store.go` 的 `OpenProducer` 校验已有任务存储而不创建或升级表；会短暂取得 schema 校验锁，不持有引擎执行锁。正常的请求计费、缓存订阅和每请求队列仍然运行；登录也会按原逻辑写登录时间和身份信息（`auth_service.go`）。本次工具变更没有给应用增加只读开关。

因此不能承诺暂停期间不写共享状态：迁移已经发生，初始化可能触碰运行文件与缓存，人工请求也会正常写数据库、共享任务存储和账本。验证时创建的异步任务可被旧后台领取；模型调用、支付、账号配置修改都有原有的实际效果，`abort` 不会撤销它们。新版本必须兼容旧后台和旧 serving 对共享数据的读写；与旧后台不兼容的任务格式或数据协议不能靠这次暂停机制安全验证，应先完成兼容设计并在隔离环境检验。不能用真实付费请求作为默认验证步骤，也不能重放结果未知的请求。

### 直接访问 serving 能验证什么

结论来自 `backend/internal/processrole/runtime.go` 的 `Wrap`、`adminPath`、`servingAdminRequest`，以及 `backend/internal/web/embed_on.go`，并非根据 Nginx 路由猜测：

| 入口 | 暂停期间的行为与验证范围 |
| --- | --- |
| `/health`、带运行令牌的 `/internal/sources/runtime` | 分别检查两个新实例；运行时必须是 serving、ready、没有后台所有权。令牌只在私有环境使用，不写进记录 |
| 镜像内嵌静态资源、登录页、用户控制台与用户 API | 直接访问服务可以加载；保留原来的认证与功能开关。检查资源加载、布局、导航、已有数据展示；登录有写入效果 |
| 普通模型 API、异步任务接口 | 仍是实际调用和正常计费；异步任务交给旧后台。默认验证清单不执行这些操作 |
| 管理页面 | 可以加载前端外壳；大部分管理 API 会在 serving 层返回 503，所以页面可能报错或缺数据，不能据此判定新版本故障 |
| 管理 API 的窄白名单 | 钱包配置、绑定、快照及监控读取/排序等部分接口可通过 serving；精确方法和路径以 `servingAdminRequest` 为准。白名单包含写操作和上游探测，不适合作为无副作用验证清单 |
| MCP 及其发现元数据、其它管理 API | 必须使用后台实例，直接访问 serving 返回 503；暂停验证不覆盖这些能力 |
| 外部服务页面、依赖公网回调或正式来源的认证流程 | 直连绕过 Nginx 和独立服务路由，本机来源也不同；不能用它证明正式入口的集成正常 |

建议先用 `status` 确认旧后台和流量仍在原槽位，再分别访问新主、新备的健康与运行时接口，检查静态资源、用户页面和已有数据读取；检查浏览器请求确实走转发后的新实例来源。管理功能、后台专属能力和完整入口集成留到切流后的守护与隔离验收。不把“页面能打开”记作完整功能验收。

### 继续、放弃与失败恢复

`resume` 先检查 `in_progress.phase=held`，核对当前版本、配置和 upstream 文件是否仍一致。它确认目标后台尚未创建，新主和新备的容器 ID 与镜像未变，容器仍在运行、就绪且隔离共享别名，旧后台仍就绪且持锁。它也复查目标后台端口、Nginx 固定 upstream、宿主可用内存和公网健康。公网健康沿用暂停时显式指定的 `--allow-public-health-failure`。能确认隔离时，验证失败仍可重试或放弃。无法确认共享别名隔离时，保存 `failed` 并告警。

工具在验证启动前记录输入文件的内容指纹，在保存暂停、继续之前和接网后交接前复核。指纹覆盖两个角色的 env 文件、实际参与解析的宿主继承变量、`CONFIG_FILE` 等文件变量引用的绑定挂载、单文件绑定挂载和只读目录挂载中的文件。env 文件中的裸变量名会继承 Docker 客户端的环境，未设置与空字符串分别记录在指纹中。通过目录挂载查找的默认 `config.*` 也会校验。`extra_env` 优先于 env 文件。可写数据或缓存目录中未被配置引用的业务文件不参与计算。状态文件只保存指纹。输入内容变化或旧暂停记录缺少这版指纹时，先放弃，再重新准备暂停。

验证通过后进入与普通发布共用的后半段。工具先保存 `phase=deploying`。需要配置共享别名时，用 Docker 解析配置中的网络名或 ID，按规范名称核对容器连接，再关闭新主、新备的自动重启。接网操作使用 Docker 返回的网络 ID。用 SIGTERM 等两台实例排空退出，给停止的容器配置所有网络及别名。确认配置齐全且网络仍存在后才启动容器，复查网络和就绪状态。继续前请结束手工验证请求。Docker 在启动容器时建立端点，应用进程尚未就绪时，经别名连接到新端点的请求可能需要重试。

进入后台交接前，工具再次核对目标端口。新后台使用暂停时记录的镜像 ID。新 serving 启动后，经共享别名的内部请求就可能进入它，此时 Nginx 仍可能指向旧 serving。

`abort` 先写入 `in_progress.phase=aborting`，只处理本次记录的 serving 和 standby。它核对容器 ID 并关闭自动重启，对仍在运行的实例发起排空。`/internal/sources/drain` 只改变就绪状态。即使实例已标记为排空，工具仍会发送 SIGTERM，让应用完成优雅退出，确认退出后才移除容器。已不存在的容器视为清理完成。遇到同名替换、目标与当前版本重叠或存在意外的目标后台时拒绝操作。只扩展的迁移、已追加的资源和验证请求产生的业务数据保留。

| 失败或中断位置 | 明确状态与恢复方式 |
| --- | --- |
| 暂停前目标槽位清理失败 | 保存 `prepare held slot` 进度，未创建暂停实例。`resume` 重试准备，成功后停在 `held` 等待验证。`abort` 放弃这次准备 |
| 新 serving 尚未就绪 | 不产生暂停；清理新 serving，旧版继续工作。清理失败保留带失败原因的 `in_progress`，核查后人工清理 |
| `resume` 的身份、镜像、网络、健康、旧后台或目标端口验证不通过 | 代理路由和容器保持原样。确认候选没有共享别名时保留 `held`，修复后重试或放弃。发现候选已挂共享别名，或 Docker 无法确认隔离时，记录 `failed` 并告警，先核对容器身份和网络 |
| 配置共享别名、启动新 serving 或交接前的复检失败 | 主备都先收到排空信号，分别确认退出，再撤回别名、补回隔离网络。隔离恢复成功后回到 `held`。若隔离网络尚缺连接，确认两个候选均已退出且共享别名已撤回后仍可 `abort`。从首次接网前开始，任何无法确认完成的排空超时都会记录 `failed` 并告警。等在途请求结束后按下文恢复 |
| 后台交接或切流失败 | 目标后台启动失败时，尝试恢复旧后台。交接后、reload 前发生故障或收到 Ctrl-C 时，先恢复已加载路由所指向的后台并确认健康与持锁。此规则也适用于切流阶段刚开始时的中断。确定候选未被代理选中时，按容器 ID 排空并停止主备。reload 结果不明时保留可能正在接流的候选。上述故障记录 `failed` 并告警，恢复仍不明确时按下文核对现场 |
| 继续后的守护失败，包括 Docker 查询异常 | 先恢复并确认旧后台可用，再回退路由并排空新 serving。旧后台无法恢复时保留可用的管理入口。`resume` 留下 `failed` 和原因，供 `watch` 告警 |
| 退役旧 serving 失败 | 新版本已在服务，保留步骤为退役的 `in_progress.phase=failed`；`current` 仍是提交完成前的旧记录。核实实际 upstream 和后台，完成旧 serving 排空，再以 `in_progress.target` 更新 current、原 current 记为 previous，最后清除标记；不要直接清空后再发布 |
| 继续的变更阶段遇到命令超时、无法执行或 Ctrl-C | 命令可能已生效。工具按当前阶段尝试恢复，确认恢复结果后才更新状态。结果仍不明时保留 `in_progress.phase=failed`，按下文人工恢复。进程被强制终止时，以最后一次保存的 `in_progress` 为准 |
| `abort` 中途失败或被中断 | `in_progress.phase=aborting` 保留；捕获到的失败写入 `reason`。后续只能重试 `abort`，不能 `resume`。修复 Docker 或权限后可重试。若进程仍在运行，重试会再次发送 SIGTERM。已移除的容器不会阻碍重试。Docker 查询失败时会保留状态 |
| 暂停期间宿主重启 | 状态文件及容器必须位于持久存储；容器沿用自动重启策略。恢复后先看 `status`，ID 和镜像不变且健康时可继续；未启动的容器先由负责人检查并启动原容器，容器丢失则放弃重发。重启不自动确认发布，也不自动清除暂停。放弃中的容器已关闭自动重启，恢复后重试放弃 |
| 容器操作结束但状态写入失败 | 命令报错。用 `status` 查看磁盘上最后保存的阶段。`held` 可继续或放弃，`aborting` 可重试放弃，`failed` 或进程已经退出的 `deploying` 需人工核查。状态已清除时先核对当前版本再决定后续操作 |
| 状态已保存，追加历史失败 | 只输出一次警告，保留已保存的状态和本次命令的退出结果。成功暂停时仍会提示 `resume` 或 `abort`。修复历史文件后按 `status` 继续操作 |

`watch` 报告 `phase=failed` 或发布进程已退出的 `phase=deploying`，告警为 `release_incomplete`。清理未完成且进程不在运行时报告 `abort_incomplete`，即使进程被强制终止而来不及写入 `reason`。健康暂停不触发发布故障告警。检测进程时核对 PID、Linux 启动标识和该进程的启动时刻，避免 PID 被复用时误判。Docker 查询失败时 `status` 显示 `unknown`，`watch` 报告 `docker_inspect_failed`。

Main 命令遇到未处理的异常时会以非零状态退出，并输出一行错误及下一步。提示以磁盘上的状态为准。配置或状态文件不可读时，先检查文件再重试。

`--dry-run` 是全局参数。`main <IMAGE_DIGEST> --hold-before-switch` 和普通 `main` 的演练一样，本地缺少镜像时会真实拉取。它会真实创建、运行、删除一次性容器来列出待迁移项，无待迁移项时也会运行一次性启动检查。有待迁移项时只打印迁移计划，跳过启动检查。迁移、资源导出、发布槽位容器操作和 Nginx 修改只打印计划。普通发布和暂停发布的演练仍会运行 `nginx -T` 做预检。`resume` 和 `abort` 演练读取现场并打印计划，不创建锁文件，不写状态、历史或修改容器。`resume` 演练只打印 `nginx -T`，因为运行该命令时 Nginx 会打开配置所引用的文件。

本节对应的本地测试使用模拟 Docker/Nginx 和应用运行时，不能代替隔离环境实测。隔离验收仍按 #31 执行，结果记录到 #39；实测通过前不用于生产。

## 自动守护与回滚

切流后检查新 serving 主实例。以下任一情况视为失败（阈值均可在配置中调整）：

- 运行时接口不再报告 `ready`；
- 容器重启或被 OOM 终止；
- 内存超过容器上限的 70%，或 30 秒内上涨超过 4 GiB；
- 公网健康检查连续 3 次失败（失败原因里写明最后一次的状态码，例如 `public health failed 3 times in a row (last status 403)`）；
- Nginx 错误日志里连接新实例端口失败（连接拒绝、upstream 超时）累计达到 10 次。

上游供应商返回的 502、503、429 不算失败：它们在切流前后都可能出现，守护只看 Nginx 能不能连上应用。

守护失败或查询抛出异常时，自动回退与 `deploy.py rollback` 共用后台交接、就绪验证和切流流程。手动回滚先记录准备阶段并检查回退后台容器存在，再隔离共享别名并启动上一槽位的主备。准备失败时保留当前路由，写入 `failed` 并告警。

确认回退槽位 serving 健康后，工具准备回退后台的重启策略，让当前后台排空退出。回退后台启动后，工具在 `background_ready_timeout` 内等待 `/health` 返回 200，并确认它就绪且持有后台锁。工具随后写入 upstream、执行 `nginx -t` 并核对就绪状态。手动回滚到曾带共享别名的槽位时，在确认目标后台和主备均就绪后才重新发布别名，复核端口后 reload。切换两个入口后，工具排空退役的 serving，再写状态和历史。交接后、reload 前出现故障或中断，先恢复原管理后台。回滚为调整别名而重连接端点时，保留 Docker 已配置的静态 IPv4、IPv6 和链路本地地址。若目标后台在最后一次检查时退出，确认原管理后台可用后只回退用户流量。自动回退保留故障槽位的容器供排查。

已进入交接、回退后台仍无法启动或就绪时，工具先检查原管理入口的后台是否仍在应答，必要时会尝试恢复它。若它可用且回退槽位的 serving 健康，只回退用户流量，管理入口保留在原后台。手动回滚若尚未恢复候选的共享别名，原 serving 继续处理内部别名流量。若候选已经发布别名，切换用户路由后向原槽位主备发送 SIGTERM，等在途请求完成且容器退出后撤下它们的共享别名。排空期间保留原来的网络连接，超时则在故障原因中保留待清理的状态。此时报告 `ROLLBACK INCOMPLETE`，`status` 和 `watch` 显示 `in_progress.phase=failed` 及原因。若两个后台都无法确认可用，则保留已加载的路由并报告 `FAILED AND NOT RESTORED`。按下文恢复后台后再改管理 upstream。

文件锁允许同时最多一个持有者。当前后台退出到回退后台就绪并切流之间仍有交接空档。整个等待期间保留已加载的 upstream，目标后台就绪后才切换。

守护只能发现切流后几分钟内的问题。常驻监测由 `deploy.py watch`（systemd 单元 `sources-main-watch.service`）负责：每 10 秒对当前版本采样健康状态、重启、OOM、内存和活跃请求数，超过阈值时向 journal 写一条预警。

## 无法自动恢复的情况

恢复失败时，`in_progress` 的 `phase` 为 `failed`，`failed_step` 和 `reason` 保留失败位置和原因，`main` 与 `rollback` 会拒绝继续。`current` 是最后一次完成发布时写入的记录，切流或退役失败后可能与线上路由不同。旧后台排空超过 `background_exit_timeout` 时，工具保留进程继续排空。它的重启策略已关闭，如果它随后退出，须人工恢复后台。

1. 暂停其他发布操作。运行 `deploy.py --config <MAIN_CONFIG> status`、`docker ps -a` 和 `docker logs <CONTAINER>`，核对 `current`、`in_progress.target`、两槽位后台状态和 upstream 配置。若 reload 结果不明，从实际入口核对路由，单看磁盘上的配置不足以判定生效结果。
2. 选择要服务的槽位。正向发布或 `rollback` 在切流前超时时，恢复交接前的后台。若状态提示用户与管理流量分处两槽，先核对仍在应答的后台，再决定完成回退或恢复到同一槽位。必要时先把非目标后台设为不自动重启（`docker update --restart=no <OTHER_BACKGROUND>`），如果后台仍在运行且尚未收到停止信号，发送 `docker kill --signal=TERM <OTHER_BACKGROUND>`。单独调用排空接口不会令进程退出。用 `docker inspect <OTHER_BACKGROUND>` 等它退出。排空中的目标后台也要等其退出后再启动。
3. 对选定的后台运行 `docker update --restart=unless-stopped <BACKGROUND>` 和 `docker start <BACKGROUND>`。确认 `/health` 返回 200，并通过 `/internal/sources/runtime` 核对 `role=background`、`ready=true` 和 `owns_background=true`。如果路由需要修复，先核对两个 serving 端口也在应答，再更新 upstream，执行 `nginx -t` 成功后 reload，检查用户入口和管理入口。
4. 排空未选中槽位的 serving，等待退出后再做必要的移除。这些实例即使不在 Nginx 路由中，也可能通过共享别名接过请求。确认实际路由与持锁后台一致后备份状态文件。若决定保留已切流的新版本，完成旧 serving 退役，把 `in_progress.target` 记为 `current`，原 `current` 记为 `previous`。恢复到原版本时保留原 `current`、`previous`。最后将 `in_progress` 改为 `null`，复查 `status`。

## 已知取舍

- 后台交接期间，后台任务暂停到新后台就绪；用户请求不受影响，新的图片任务照常受理并在新后台起来后执行。管理读接口在旧后台排空期间照常可用，从旧后台关闭监听到新后台就绪并切流期间不可用；管理写操作和 MCP 要等新后台就绪，期间返回 503。旧后台上正在进行的长任务（例如定时备份）只延长写操作的等待。
- 守护只覆盖切流后的短时间窗口，较晚出现的问题依赖常驻监测和 serving 的主备结构。
- 只在后台持锁时才执行的分支（应用迁移、以引擎方式打开媒体引擎）无法被 `-check-startup` 覆盖，由后台交接的自动回退兜底。
- 本方案针对单台主机。若以后扩展到多台主机，可以把文件锁换成 PostgreSQL 会话级 advisory lock（连接断开时同样自动释放），其余设计不变。

## Portal

Portal 用同一个工具发布：`deploy.py portal <镜像>`，代码在 `deploy/sources/portal.py`，命令和失败处理见 [deploy/sources/README.md](../../deploy/sources/README.md) 的“Portal”一节。它与 Main 的设计有三点不同。

**一个容器，一段无法避免的不可用。** Portal 的状态目录只有一个写入者：进程启动时对状态目录加非阻塞文件锁，第二个进程拿不到锁会立即以代码 1 退出；监听端口在锁和全部存储初始化之后才打开，所以新进程在旧进程退出之前无法回答 `/health`。因此不能像 Main 的 serving 那样先启动新实例再切流，从旧 Portal 收到 SIGTERM 到 Nginx 切到新容器之间，Portal 的页面不可用。工具把所有能提前做的事放在发信号之前（拉取镜像、预检、`-check-config` 启动检查、创建新容器），旧进程一退出就启动新容器，每 0.25 秒检查一次，新容器 `/health` 返回 200 就立即切换 Nginx。旧 Portal 收到 SIGTERM 后立即关闭监听，处理完在途请求后退出（通常几秒，极少数同步余额刷新最长约 375 秒）。工具从不发送 SIGKILL，Docker 也不会重启被 `docker kill --signal=TERM` 停下的容器，所以信号发出后只能等它退出再启动容器：超过 `exit_timeout`（默认 420 秒）每 30 秒打印警告并继续等待，旧进程一退出就照常继续；超过 `exit_abort_timeout`（默认 3600 秒）才停止，保留 `in_progress`，新容器已创建但未启动、Nginx 未改动，Portal 在旧进程退出前一直不可用，由运维人员在它退出后 `docker start` 旧容器恢复服务再清除 `in_progress`。当前容器在交接时已经不在运行（例如崩溃）则不发信号，直接启动目标容器，所以 `portal-rollback` 在当前 Portal 崩溃时同样可用。交接到守护之间的命令超时、命令无法执行和 Ctrl-C 中断都按失败处理：先回退到旧容器，再以错误结束。

**应用提供的支持。** Portal 只有 `GET /health`（200 `{"status":"ok"}` 或 503），没有 Main 的运行时接口、角色、令牌和排空。新镜像提供 `/app/sources-portal -check-config`：只读的启动检查，不取锁、不写任何东西、不打开监听端口，校验环境变量和磁盘上的状态，成功时输出 `SOURCES_PORTAL_CONFIG_OK` 并以 0 退出，失败时输出一行错误并以 1 退出。工具用真实的环境和挂载（全部强制只读）运行它，在碰旧容器之前就发现配置错误。没有该参数的旧镜像会按正常启动处理、拿不到锁而失败，工具同样视为检查失败。

**固定结构。** 两个槽位 A、B 轮流使用，容器名为 `<前缀>-{a,b}`，每个槽位的本机端口在 `portal.json` 中固定；Nginx 只引用固定的 `upstream sources_portal`，切流时只重写这个 upstream 文件（与 Main 相同的“写入、`nginx -t`、失败恢复原文件、成功 reload”顺序）。首次接入用 `portal-adopt` 记录运行中的容器（槽位 `legacy`，工具从不删除它）。交接后任何失败都按“停新容器（它持有锁）→ 启动旧容器并等 `/health` → 如已切流则切回”回退；回退本身失败时报告 `FAILED AND NOT RESTORED` 并保留 `in_progress`。`portal-rollback` 用同样的流程切回上一容器，但较旧的 Portal 可能拒绝较新版本写下的状态，此时自动回到当前版本。

Portal 和 Main 共用一把发布锁（`portal.json` 与 `main.json` 的 `lock_file` 是同一个文件），两者的发布不会重叠。

**切流后的检查与状态。** Nginx reload 返回时旧 worker 可能仍在接受连接。Portal 在切流阶段先等公网健康返回 200，成功响应后按等待开始时的启动时间和重启次数复核容器，确认仍在运行、未处于重启中且没有被 OOM 终止，再开始完整守护时长与失败计数；等待复用 `ready_timeout`，期间新容器停止、重启（包括探测返回 200 之前发生的重启）、被 OOM 终止或等待超时，均按原流程回退。`portal-status` 在发布进行中把 `current`、`previous` 标为本次发布之前的记录，并在独立的 `target` 项展示目标容器的实时状态，守护阶段可直接查看正在服务的目标；已停止的容器不显示过期的健康状态。
