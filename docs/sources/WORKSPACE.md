# 分支、工作区与文档规范

`main` 始终可交付；每项开发使用按类型命名的短期分支，完成后合并并删除。

## 开始与同步

1. 先确认当前目录、分支和未提交内容，避免在别人的工作上继续。
2. 同步 `main`：`git fetch origin` 后 `git merge --ff-only origin/main`。有分歧或本地修改时先弄清归属并保存，不强制覆盖。
3. 从最新 `origin/main` 创建短期分支，例如 `fix/deepseek-stream-timing`；不要在旧功能分支上顺手继续新任务。
4. 需要并行处理多项任务时，每项任务使用独立的 worktree：`git worktree add -b fix/<主题> <目录> origin/main`。主工作目录只用于阅读和快进同步。

## 分支命名

采用轻量主干开发：`main` 可交付，短期分支经审查和验证后合并。不引入常驻 `develop`、多层合并或没有用途的 release 分支。

| 前缀 | 用途 | 示例 |
| --- | --- | --- |
| `feature/` | 新能力 | `feature/wallet-alerts` |
| `fix/` | 已有行为的缺陷修复 | `fix/deepseek-stream-timing` |
| `perf/` | 不改变功能语义的性能优化 | `perf/usage-query` |
| `refactor/` | 不改变对外行为的结构调整 | `refactor/tool-executor` |
| `docs/` | 纯文档 | `docs/development-guide` |
| `chore/` | 工具、依赖、工程维护 | `chore/update-lint-rules` |

- 格式为 `<type>/<可选 issue 号->英文短主题>`，小写、连字符；不放人名、密钥、日期或版本号。有真实 issue 时才写编号。
- 统一使用 `feature/`，不同时使用 `feat/`。提交信息仍用 Conventional Commit 的 `feat:`、`fix:` 等，分支前缀和提交类型不必逐字相同。
- 修复中顺带的性能改善仍用 `fix/`。紧急修复也用 `fix/`，紧急程度由发布流程表达，不设常驻 `hotfix` 分支。
- 不建立长期 `dev` 或 `develop` 集成分支。测试随所属改动提交；独立的测试基础设施用 `chore/`。
- 已有的历史分支名不为统一而批量改名。

## Issue 与 PR

issue 记录要做什么、为什么做，PR 记录怎么做的、验证了什么。待办只记在 issue 里：聊天记录和临时 TODO 在会话结束后没有人会再看到。

### 流程

1. **开 issue。** 准备做的事，以及不是马上就做的事（顺手发现的缺陷、评审中推迟的后续工作、想法），发现时当场就开。网页上用仓库的表单（缺陷、新功能、任务）；用 `gh issue create` 时不经过表单，同样写清现象或目标、验收标准，并打上类型标签。
2. **建分支。** 从最新 `origin/main` 创建 `<type>/<主题>`，可以把编号放在主题前，例如 `fix/123-stream-timing`。
3. **开 PR。** 正文的 `Issue:` 一行写 `Closes #N`。网页上新建 PR 时模板会给出这一行；`gh pr create --body` 不使用模板，要自己写上。
4. **合并。** PR 合并进 `main` 时，GitHub 自动关闭用 `Closes` 或 `Fixes` 关联的 issue，不用手工关。修复不成立时重新打开原 issue；新出现的后续工作另开 issue。

### PR 正文的写法

| 情况 | 写法 |
| --- | --- |
| 这个 PR 做完了 issue | `Closes #12`，缺陷也可以写 `Fixes #12` |
| 一个 PR 关闭多个 issue | 每个编号前都写关键字：`Closes #12, closes #15`。写成 `Closes #12, #15` 只会关闭第一个 |
| 一个 issue 分几个 PR 完成 | 前面的 PR 写 `Refs #12`，最后一个写 `Closes #12`；各步骤在 issue 里用任务清单列出 |
| 相关但不解决 | `Refs #12` |
| 没有 issue | `No issue: <原因>` |

- 关键字写在 PR 正文里。检查只读正文，不读标题和提交信息。
- 可以写 `No issue` 的只有四类：错别字、纯文档小改、依赖或 CI 的机械维护、发版准备 PR。原因用一句话说明属于哪一类，例如 `No issue: 修正开发指南里的命令拼写`。拿不准时就开 issue。
- CI 的 `issue-link` 作业运行 `scripts/sources_extensions/check_pr_issue.py`：正文里既没有关键字加编号，也没有 `No issue:` 加原因时，`ci` 不通过。它只检查写了没有；编号是否对应真实的 issue、原因是否属于上面四类，由评审判断。
- 修改正文不会自动重新运行检查。改完后等这次运行结束，重新运行失败的作业（检查页上的按钮，或 `gh run rerun <运行编号> --failed`），它读取的是当前的正文；推送新的提交也会重新检查。

### 标签

每个 issue 打一个类型标签，名称与分支前缀对应。

| 标签 | 用途 | 对应分支 |
| --- | --- | --- |
| `bug` | 已有行为的缺陷 | `fix/` |
| `feature` | 新能力，或对已有能力的改进 | `feature/` |
| `chore` | 工具、依赖、CI、重构、性能等工程维护 | `chore/`、`refactor/`、`perf/` |
| `docs` | 纯文档 | `docs/` |
| `release-blocker` | 下一个版本发布前必须解决，与类型标签叠加 | 不限 |

发版前，发布负责人逐个确认仍未关闭的 `release-blocker`。

### 里程碑

建议默认不使用版本里程碑，不强制：

- 版本号在发版时由发布负责人确定，合并到 `main` 不自动发版。提前把 issue 归到某个版本，等于多维护一份容易过期的计划。
- 一个版本包含了什么，已经由 `CHANGELOG.md` 记录；发版前必须解决的事项，用 `release-blocker` 表达。
- 某个版本确实有事先约定的范围时（例如一次上游同步，或必须一起发布的一组改动），可以为它单独建一个里程碑，发版后关闭。

### 公开边界

issue、评论和 PR 正文与代码一样公开，适用 [AGENTS](../../AGENTS.md) 的“公开仓库的边界”。

- 写：哪个功能在什么输入或配置下行为不对、期望的行为、怎样复现、验收标准。示例使用占位值或合成数据。
- 不写：发生在哪台机器、哪个域名、哪个上游，涉及哪个用户、多少金额或多少条记录，以及事故的经过。这些属于运维资料，记在私有仓库；公开 issue 只需要足以修改代码的描述。
- 日志和截图先脱敏再贴。已经发出的敏感内容不要只是编辑掉，编辑历史仍然可见，应报告维护者处理。
- 安全漏洞不开公开 issue，使用仓库的私密漏洞报告。

## 开发、提交与合并

- 一个分支处理一个明确目标。临时 SQL、私有配置、下载文件、缓存和原始日志不放进仓库，也不要整包 `git add`。
- 新增、改变或退出一项二开能力时更新 [SOURCES](../../SOURCES.md)；核心文件变化更新 [CORE-PATCHES.json](CORE-PATCHES.json)。
- 提交信息使用简短英文 `type: summary`。纯文档提交可以加 `[skip ci]`；功能、计费或运行逻辑的变更不能靠跳过 CI 合并。
- 合并只带当前任务的改动。旧分支先与最新 `main` 比较，不整文件覆盖较新的实现。
- `main` 受保护时通过 PR 合并，不强推绕过。已提交、已推送、已合并、已发布是不同状态。

## 收尾与清理

1. 确认改动已合并或明确取消；未完成的事项记录到 issue 或对应设计文档。
2. 删除分支前核对它是否还有独有提交；squash 合并后不能只靠祖先关系判断。删除远端分支时用期望的提交 SHA 约束，避免删掉别人的新提交。
3. 工作树干净且不再需要时用 `git worktree remove` 删除。未提交或被忽略的文件要先单独保存：bundle 不包含未提交和被忽略的文件，patch 不包含完整的新文件。
4. 已发布的 tag 和镜像不改写、不覆盖。

## 文档分工

| 入口 | 职责 |
| --- | --- |
| `AGENTS.md` | 贡献与 Agent 的长期规则 |
| `DEV_GUIDE.md` | 工具链、目录结构、开发命令、验证方法 |
| `SOURCES.md` | 相对原版的能力差异及代码入口 |
| `CHANGELOG.md` | 各版本面向用户的变化 |
| `docs/sources/README.md` | 二开文档索引 |
| `docs/sources/*.md` | 单项能力的设计：为什么做、怎么做、怎么验证 |

仓库根目录不放 `PLAN.md`、`progress.md`、`task_plan.md`、`findings.md` 之类的临时状态文件。有价值的结论写进对应的设计文档。具体某次发布、事故或核对的执行记录属于运维资料，不放进本仓库。文档只链接仓库内实际存在的文件。
